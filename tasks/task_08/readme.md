## Цель работы

Построить «глаза» для своего сервиса: развернуть систему мониторинга в
Kubernetes, экспонировать метрики приложения, включить трейсинг через
OpenTelemetry, собрать дашборды, настроить алерты по SLO своего варианта
и упаковать всё в Helm-чарт.

## Результаты обучения

После выполнения работы вы будете уметь:

- разворачивать kube-prometheus-stack (Prometheus, Grafana, Alertmanager) через Helm;
- добавлять в приложение метрики counter/gauge/histogram и endpoint `/metrics`;
- подключать сбор метрик через ServiceMonitor и проверять его в Prometheus;
- включать OpenTelemetry-трейсинг и читать путь запроса по span'ам;
- строить дашборды доступности, задержек p95/p99 и ошибок в Grafana;
- писать PrometheusRule-алерты по SLO и проверять их срабатывание;
- параметризовать деплой Helm-чартом.

## Быстрый первый успех (30–40 минут)

Первый работающий результат до всякого кода:

1. Запустите кластер: `minikube start` (или kind).
2. Установите мониторинг одной командой:

   ```bash
   helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
   helm repo update
   helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
   ```

3. Пробросьте Grafana: `kubectl port-forward svc/monitoring-grafana 3000:80 -n monitoring`
   (логин `admin` / `prom-operator`).
4. Откройте готовые дашборды кластера (CPU/память узлов и подов) — они
   работают из коробки.

У вас уже есть живая система мониторинга. Дальше вся работа — научить её
видеть **ваше** приложение.

## Теоретическая справка (кратко)

- **Три сигнала**: метрики («что происходит»), трейсы («где в цепочке»),
  логи («почему»). В этой работе — метрики и трейсы.
- **Prometheus** забирает метрики pull'ом с endpoint `/metrics`;
  **ServiceMonitor** говорит ему, какие сервисы опрашивать; **Grafana**
  рисует; **Alertmanager** доставляет алерты.
- **OpenTelemetry** — единый стандарт телеметрии: SDK с
  автоинструментацией + протокол OTLP; код инициализации — в лекции 24.
- **SLI/SLO/бюджет ошибок и burn rate** — сердце алертинга: алерт должен
  реагировать на скорость потери обещания, а не на каждый чих.
- Полная теория — лекция 24 «Наблюдаемость» (`curriculum/`), детали
  команд — [методические материалы](./Лабораторная_работа_08_Методические_материалы.md).
  Признаки необходимости масштабирования (saturation, p95) и нагрузочное
  тестирование — лекция 26.

## Задания

1. Установить систему мониторинга:
    - Развернуть kube-prometheus-stack в namespace `monitoring` с помощью Helm;
    - Проверить доступность Prometheus, Grafana и Alertmanager;
    - Настроить доступ к Grafana (port-forward или Ingress).
2. Добавить метрики в приложение:
    - Интегрировать client-библиотеку Prometheus в приложение из лаб 5–6;
    - Создать endpoint `/metrics` с префиксом метрик согласно варианту;
    - Экспонировать базовые метрики: счётчик запросов, гистограмму задержек, gauge для статусов;
    - Создать ServiceMonitor или PodMonitor для автоматического обнаружения метрик.
3. Включить OpenTelemetry-трейсинг:
    - Подключить OTel SDK с автоинструментацией HTTP (пример инициализации — лекция 24, § 5);
    - Экспортировать span'ы в Tempo/Jaeger (или в консольный экспортер, если бэкенд не разворачиваете);
    - Приложить скриншот/фрагмент трейса запроса с ≥ 2 span'ами.
4. Создать дашборды и алерты:
    - Разработать 2-3 дашборда в Grafana:
      - Доступность сервиса (availability);
      - Задержка p95/p99;
      - Частота ошибок 5xx.
    - Настроить 1-2 PrometheusRule с алертами по SLO из варианта (доступность, latency, error rate);
    - Проверить срабатывание алерта (симуляция нагрузки или ошибок).
5. Упаковать приложение в Helm-чарт:
    - Создать чарт с параметризацией: namespace, replicas, port, resources, ingressClass, метрики (prefix);
    - Templates: Deployment, Service, Ingress, ServiceMonitor, PrometheusRule;
    - Валидация: `helm lint`, `helm template`, успешная установка.

## Контрольные вопросы для защиты

1. Чем наблюдаемость отличается от мониторинга? Какие вопросы закрывают
   метрики, логи и трейсы? (лекция 24)
2. Почему Prometheus использует pull-модель и как он замечает падение
   сервиса? Что делает ServiceMonitor?
3. Какие типы метрик вы использовали и почему? Почему counter смотрят
   через `rate()`?
4. Что такое кардинальность меток? Какая метка в вашем приложении могла
   бы «взорвать» Prometheus?
5. Расшифруйте свой SLO из варианта: что такое бюджет ошибок и чему он
   равен у вас? (лекция 24)
6. Покажите ваш PrometheusRule: почему выбрано именно это окно и порог?
   Что такое alert fatigue и burn rate?
7. Покажите ваш трейс: как связаны trace и span? Как контекст трейса
   попадает из HTTP-запроса в span'ы? Зачем семплирование?
8. Как ваш дашборд отличает «сервис деградирует» от «сервис мёртв»?
   Какие метрики укажут на необходимость масштабирования? (лекция 26)
9. Что параметризует ваш values.yaml? Как переиспользовать чарт для
   другого варианта, не трогая templates?
