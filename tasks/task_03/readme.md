## 🚀 Быстрый первый успех (15 минут)

Пример из [examples/](examples/) **сломан из коробки — так задумано**:
circuit breaker выключен (`BREAKER=off`). Заморозьте сервис тревог — и
каждое показание будет висеть на таймаутах. Все команды — Windows
PowerShell, копируются построчно.

```powershell
# 1. Проверка окружения (Docker Desktop должен быть запущен)
docker version

# 2. Перейти в папку примера (внутри клона репозитория курса)
cd tasks\task_03\examples

# 3. Поднять стенд лабы 2 + новая оборона: devices -> alerts
docker compose up --build -d

# 4. Убедиться, что оба контейнера healthy (иначе подождите ~10 секунд и повторите)
docker compose ps

# 5. Steady state: тревога доставляется мгновенно
Invoke-RestMethod -Method Post -Uri http://localhost:8080/readings -ContentType "application/json" -Body '{"device_id":"dev-7","sensor":"temperature","value":72.5}'

# 6. Впрыск сбоя: заморозить alerts (контейнер жив, но процесс не отвечает)
docker compose pause alerts

# 7. То же показание — теперь запрос ВИСИТ ~2 секунды (все таймауты и попытки)
Measure-Command { Invoke-RestMethod -Method Post -Uri http://localhost:8080/readings -ContentType "application/json" -Body '{"device_id":"dev-7","sensor":"temperature","value":73.0}' } | Select-Object TotalSeconds

# 8. Повторите шаг 7 ещё пару раз: висит КАЖДЫЙ запрос. Это каскад:
#    один замороженный сервис тянет на дно всех, кто его зовёт.

# 9. Чиним: включаем circuit breaker и пересоздаём devices
docker compose unpause alerts
$env:BREAKER = "on"
docker compose up -d devices
```

Теперь повторите шаги 6–7: первые три запроса медленные (breaker набирает
статистику ошибок), а дальше — **мгновенные** ответы `202` с
`degraded=true`: breaker открылся, тревоги уходят в локальную очередь.
Верните alerts (`docker compose unpause alerts`) — через несколько секунд
breaker закроется и очередь доедет сама, без дублей. Состояние смотрите в
`Invoke-RestMethod http://localhost:8080/health`.

Если вы увидели разницу «висит ~2 с» → «отвечает мгновенно» — вы
воспроизвели главную проблему лабы и её решение. Дальше делаете то же самое
своими руками для **своей** пары сервисов из лабы 2.

⚠️ Типичные проблемы на этом шаге:

* `error during connect ... pipe/dockerDesktopLinuxEngine` — Docker Desktop не запущен; запустите его и дождитесь зелёного кита.
* Порт 8080 или 8081 занят — поменяйте левую часть `ports:` в `compose.yaml` (например, `18080:8080`) и подставьте новый порт в команды.
* После `docker compose pause` забыли `unpause` — контейнер так и стоит замороженным; `docker compose ps` покажет `(Paused)`.

## Теоретическая справка (кратко)

Полная теория — в [лекции 09](../../curriculum/Лекция_09_Отказоустойчивость_и_chaos_engineering.md),
справочник с диаграммой автомата, кодом и отладкой — в
[методических материалах](./Лабораторная_работа_03_Методические_материалы.md).
Минимум для лабы:

* **Каскадный отказ:** зависший сервис держит соединения и потоки всех, кто его зовёт; очереди растут, ретраи умножают нагрузку — авария расползается по цепочке, хотя «никто не ошибся».
* **Ретраи ≠ breaker.** Ретраи (лаба 2) лечат короткий сбой — моргнула сеть. Когда зависимость лежит минуты, ретраи только добивают её и держат вызывающего. Breaker замечает, что «всё плохо надолго», и отказывает мгновенно (fail fast).
* **Три состояния breaker'а:** CLOSED — вызовы идут, ошибки считаются в окне; OPEN — вызовы запрещены, мгновенный отказ; HALF-OPEN — после паузы восстановления пропускается ограниченное число проб: успех → CLOSED, провал → снова OPEN.
* **Деградация вместо 500:** пользователь не должен страдать из-за лежащей зависимости. Тревогу — в локальную очередь, пользователю — честный «принято, доставим» (202), после восстановления — догон. Ключ идемпотентности из лабы 2 делает догон безопасным.
* **Backpressure:** одновременность ограничена (семафор/очередь с лимитом); сверх лимита — честный `503` + `Retry-After`. Бесконечный буфер не спасает — он лишь оттягивает и укрупняет отказ.
* **Канон chaos-эксперимента:** определить steady state → письменная гипотеза → минимальный blast radius → впрыск с планом отката → измерить → починить → повторить.

## Задание

Работа **продолжает вашу лабу 2**: та же пара сервисов caller → callee, тот
же номер варианта. Параметры сбоя, breaker'а, fallback и лимита — по вашему
варианту из [Варианты.md](./Варианты.md). Вариант 0 (эталон преподавателя,
devices → alerts) — в [examples/](examples/): копировать его сценарий и код
в сдачу нельзя.

### Часть 1. Стенд из лабы 2 и каскад «до»

Перенесите свою пару сервисов из лабы 2 (таймауты, ретраи и Idempotency-Key
уже должны работать) и покажите проблему:

* сократите ретраи клиента до 1–2 попыток (объясните в отчёте, почему при живом breaker'е длинные ретраи вредны);
* уберите `depends_on` c ожиданием готовности callee, если оно было: caller обязан стартовать и жить без callee;
* **воспроизведите каскад:** заморозьте callee (`docker compose pause`), отправьте серию из ≥ 5 запросов к caller и замерьте каждый (`Measure-Command`). Таблица «запрос → задержка → исход» — обязательный артефакт «до».

### Часть 2. Circuit breaker

* Реализуйте breaker на клиенте caller → callee: своя реализация (образец ~80 строк — `examples/devices/app/breaker.py`) или библиотека — но каждый параметр объяснён в отчёте;
* состояния CLOSED / OPEN / HALF-OPEN; параметры варианта: порог ошибок, окно, таймаут восстановления, лимит проб в HALF-OPEN — через переменные окружения;
* ошибкой считаются сетевые ошибки, таймауты и 5xx (после всех ретраев попытки);
* журнал переходов и счётчики (allowed/rejected/success/failure) — в `/health` или логах;
* **покажите полный цикл** логом/скриншотом: `closed → open → half-open → closed` (и хотя бы один `half-open → open` — проба при ещё лежащем callee).

### Часть 3. Fallback, деградация и догон

* При отказе вызова (breaker OPEN или вызов провалился) запись уходит в локальную очередь по варианту (файл jsonl или Redis-список), а клиент caller получает деградированный ответ `202` с маркером (`degraded: true`), **а не 500**;
* очередь ограничена (лимит — переменная окружения); переполнение → честный `503`;
* фоновый догон: после восстановления callee очередь доставляется автоматически; ключ идемпотентности генерируется **до** первой живой попытки и сохраняется в очереди — докажите логом, что догон не создал дублей;
* артефакт «после»: тот же сценарий, что в части 1, — при лежащем callee ответы мгновенные, после восстановления все записи на месте, дублей нет.

### Часть 4. Backpressure

* Ограничьте число одновременных обработок «дорогих» запросов лимитом варианта (семафор asyncio / счётчик в Node);
* при занятых слотах — немедленный `503` с заголовком `Retry-After` (значение — из варианта);
* эксперимент: ≥ 10 параллельных клиентов при лежащем callee и выключенном breaker'е (образец — `examples/devices/app/pressure_demo.py`); таблица исходов: сколько запросов заняли слоты и висели, сколько получили мгновенный 503;
* в отчёте — вывод: что было бы без лимита (куда девались бы запросы и чем это кончается).

### Часть 5. Мини-chaos эксперимент

По канону лекции 09 — письменно, в отчёте (образец сценария —
`examples/chaos_demo.ps1`):

* **steady state:** какой показатель считаете нормой (например, «p95 ответа caller < 200 мс, записи не теряются») и его измеренное значение до впрыска;
* **гипотеза:** «при сбое callee типа X caller продолжит отвечать быстрее Y мс, записи не потеряются» — записана ДО эксперимента;
* **впрыск:** сбой вашего варианта (`stop` / `pause` / окно задержки / окно 5xx) с минимальным blast radius и планом отката;
* **наблюдение:** таблица «запрос → задержка → исход → состояние breaker'а» в **двух прогонах** — без breaker'а и с ним;
* **откат и вывод:** подтвердилась ли гипотеза, чем прогоны отличались, что бы вы изменили в параметрах breaker'а. Логи обоих прогонов — обязательный артефакт (`logs/chaos_before.txt`, `logs/chaos_after.txt`);
* для сбоев, которые отказывают быстро (`stop`, окно 5xx), сравнивайте не только задержку, но и **число запросов, дошедших до callee** (счётчики/логи callee): breaker снимает нагрузку с лежащей зависимости, даже когда клиенту и так «быстро плохо».

## Бонусы (+ до 15)

* **Медленные ответы — тоже ошибки** (+5) — breaker учитывает slow calls: ответы дольше порога считаются отказами; эксперимент с окном задержки callee (ответы успешные, но медленные) — breaker открывается; порог и лог — в отчёте.
* **Приоритетный shedding** (+4) — два класса запросов (например, телеметрия и тревоги): при переполнении сбрасывается только неприоритетный класс, приоритетный — никогда; доказано экспериментом.
* **Метрики `/metrics`** (+3) — счётчики в текстовом формате Prometheus: состояния breaker'а, отклонённые 503, размер очереди fallback; значения после эксперимента — в отчёте.
* **Второй тип сбоя** (+3) — дополнительный chaos-прогон с другим типом сбоя (не из варианта); сравнение в отчёте: «умер» vs «завис» vs «медленный» — как быстро каждый замечается клиентом и breaker'ом.

## Зачем в реальных системах

| Что делаете в лабе | Где это в производстве |
| --- | --- |
| Circuit breaker | Стандарт любого межсервисного вызова: Resilience4j (Java), Polly (.NET), Envoy/Istio outlier detection; сбой Google Cloud 12.06.2025 растянулся на часы в том числе из-за шторма повторных запросов к лежащему сервису |
| Fail fast | Мгновенный отказ освобождает потоки и соединения; медленный отказ держит ресурсы всей цепочки — так один сервис кладёт платформу |
| Fallback и деградация | Amazon и Netflix отдают урезанный ответ (кэш, заглушка, очередь) вместо ошибки; «тревога в очередь» — ровно то, что делает Hub «СмартДома» при обрыве связи с облаком |
| Догон + идемпотентность | Любая офлайн-очередь (мобильные приложения, IoT-шлюзы, платёжные системы) доставляет накопленное после восстановления — без ключей идемпотентности это источник дублей |
| Backpressure + Retry-After | Load shedding в Google SRE: перегруженный сервис отвечает быстро и честно, а не копит очередь до OOM; `Retry-After` — стандартный способ сказать клиенту «приходи позже» |
| Chaos-эксперимент | Chaos engineering (Netflix Chaos Monkey, Chaos Mesh, Gremlin): сбои впрыскивают в проде специально и регулярно, чтобы находить слабости до того, как их найдёт реальная авария |

## Контрольные вопросы для защиты

1. Что такое каскадный отказ и почему он возникает, хотя «никто не ошибся»? Покажите каскад на своей таблице «до».
2. Назовите три состояния circuit breaker'а и условия всех переходов — с числами вашего варианта.
3. Почему ретраи не заменяют breaker, а breaker — ретраи? Какой сбой лечит каждый механизм?
4. Как вы выбрали порог ошибок и окно? Что изменится при пороге 1? При окне в 1000 вызовов?
5. Что такое fail fast и почему мгновенный отказ дешевле медленного? Где это видно в ваших замерах?
6. Зачем в HALF-OPEN ограничивать число проб? Что случится, если после паузы пустить в лежащий сервис всех сразу?
7. Чем «завис» (pause) отличается от «умер» (stop) с точки зрения вашего клиента? Почему таймауты обязаны считаться ошибками breaker'а?
8. Как ваш догон гарантирует отсутствие дублей? Когда генерируется Idempotency-Key и где он хранится, пока callee лежит?
9. Что такое backpressure и почему честный 503 + Retry-After лучше бесконечной очереди «мы вам перезвоним»?
10. Перечислите шаги канона chaos-эксперимента. Какой была ваша гипотеза и подтвердилась ли она?
