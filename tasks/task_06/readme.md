# Лабораторная работа №6. Kubernetes: состояние и хранение

**Дисциплина:** Распределённые системы и облачные технологии (РСиОТ)
**Тема:** StatefulSet, PVC/StorageClass, Headless Service, резервное
копирование и проверенное восстановление

---

> 🚀 **Окружение — из лабы 5:** Docker Desktop + kubectl + kind уже
> установлены ([QUICK_START лабы 5](../task_05/QUICK_START.md)). Первый
> работающий StatefulSet — за 30–40 минут по Части 1.

## Цель работы

Дать платформе «СмартДома» настоящую память: развернуть stateful-сервис
(PostgreSQL/Redis по варианту) через StatefulSet с постоянным хранилищем,
проверить сохранность данных при пересоздании подов и построить контур
«бэкап по расписанию → **проверенное** восстановление» с фиксацией
RPO/RTO.

## Результаты обучения

После выполнения работы студент будет:

- уметь описывать StatefulSet с `volumeClaimTemplates` и Headless
  Service;
- понимать цепочку PVC → StorageClass → PV и режимы доступа;
- уметь доказывать сохранность данных экспериментом (удаление пода,
  удаление StatefulSet с сохранением PVC);
- строить бэкап CronJob'ом и восстановление Job'ом — и **тестировать**
  восстановление;
- формулировать RPO/RTO для конкретного сервиса.

## Лекции-основы

- **Лекция 19.** K8s: состояние и хранение — PV/PVC/StorageClass,
  StatefulSet, Headless, слои защиты данных, 3-2-1.
- **Лекция 10.** Хранилища данных в РС — какие данные в какую модель.
- **Лекция 16.** Shared responsibility: за данные отвечаете вы;
  «репликация ≠ бэкап».

## Теоретическая справка (кратко)

- Данные хранит **PVC/PV**, а не контроллер: под смертен, том — нет.
- **StatefulSet** добавляет к Deployment: стабильные имена
  (`db-0, db-1`), персональный PVC каждой реплике
  (`volumeClaimTemplates`), упорядоченные операции. Репликацию СУБД он
  **не** настраивает.
- **Headless Service** (`clusterIP: None`) даёт DNS-имя каждому поду:
  `db-0.db-hl.<ns>.svc.cluster.local`.
- **Бэкап ≠ реплика**: реплика тиражирует и вашу ошибку; логический dump
  переносим, снапшот быстр; непроверенное восстановление — не бэкап.
- **RPO** — сколько данных допустимо потерять (интервал копий);
  **RTO** — за сколько восстановиться.

Полная теория — лекция 19 (`curriculum/`); методичка 2025 года —
[справочник](Лабораторная_работа_06_Методические_материалы.md).

## Задание

Параметры — по вашему варианту из [Варианты.md](Варианты.md): СУБД
(PostgreSQL или Redis), размер PVC, имя StorageClass, cron-расписание
бэкапа. Вариант 0 (эталон преподавателя, PostgreSQL «СмартДома») — в
[examples/](examples/): копировать 1:1 нельзя.

### Часть 1. Быстрый первый успех: данные переживают под (30–40 минут)

1. В кластере из лабы 5 (`kind create cluster --name smartdom`, если
   снесли) примените эталон: `kubectl apply -f examples/k8s/`.
2. Запишите тестовое показание в БД (команды — в
   [examples/README.md](examples/README.md)).
3. Убейте под: `kubectl -n smartdom delete pod smartdom-db-0` —
   дождитесь пересоздания и убедитесь, что запись на месте.
4. Скриншот «до/после» — ваша точка опоры: главный фокус лабы
   воспроизведён.

### Часть 2. Свой StatefulSet по варианту

1. Опишите в `k8s/`: `namespace`, `secret` (пароль СУБД — не в
   манифесте пода!), Headless Service, StatefulSet с
   `volumeClaimTemplates` (размер и storageClassName — из варианта;
   для kind создайте свой StorageClass-алиас на провижионер
   `rancher.io/local-path`, как в examples).
2. Для PostgreSQL не забудьте `PGDATA` в подкаталог тома; для Redis —
   `appendonly yes` (иначе бэкапить нечего).
3. Метки и аннотации `org.bstu.*` (как в лабе 5), namespace
   `state-<slug>`.

### Часть 3. Доказательство сохранности

1. Создайте тестовые данные (таблица/ключи с осмысленными значениями
   «СмартДома»: показания, устройства).
2. Эксперимент 1: `kubectl delete pod <db>-0` → данные на месте
   (скриншоты до/после).
3. Эксперимент 2: `kubectl delete statefulset <имя>` (PVC остаются!) →
   пересоздайте StatefulSet манифестом → данные на месте. Объясните в
   отчёте, почему PVC пережил контроллер.

### Часть 4. Бэкап и проверенное восстановление

1. **CronJob** с расписанием из варианта: логический бэкап (`pg_dump` /
   `redis-cli BGSAVE` + копия RDB) в **отдельный** PVC для бэкапов.
2. Убедитесь, что CronJob реально отработал (`kubectl get jobs`,
   логи; для проверки можно временно поставить `*/2 * * * *`).
3. **Тест восстановления**: удалите данные (например, `DROP TABLE` —
   осознанно!), запустите restore-Job из последней копии, покажите
   данные на месте.
4. Зафиксируйте в отчёте измеренные **RPO** (интервал расписания) и
   **RTO** (время от запуска restore-Job до готовности данных,
   засеките).

## Бонусы (+ до 15)

* **Бэкап в объектное хранилище** (+5) — MinIO в кластере или внешний

## Правила защиты и использование ИИ

ИИ-инструменты использовать **можно**. Обязательно: раздел
«Использование ИИ» в отчёте (что генерировали, что проверили руками;
«не использовал» — допустимо); на защите вопросы — по **вашим**
манифестам и скриптам; незнание своей сдачи = несдача.

## Пересдача

Исправление замечаний — в течение **одной недели** после проверки;
максимум при пересдаче — **85 %** исходного балла. Соревновательных
рейтингов нет.

## Контрольные вопросы для защиты

1. Покажите в ваших манифестах, кто создаёт PVC и когда именно.
2. Почему данные пережили удаление StatefulSet? Всегда ли так будет?
3. Чем Headless Service отличается от обычного и зачем он StatefulSet?
4. Что произойдёт при `kubectl delete pvc` с вашим StorageClass?
5. Почему пароль СУБД — в Secret, а не в env StatefulSet напрямую? Чем
   Secret всё равно небезопасен?
6. Ваш RPO по варианту — какой? Какие данные «СмартДома» его не
   переживут?
7. Чем логический dump отличается от снапшота тома?
8. Почему реплика не заменяет бэкап? Приведите кейс из лекций.
9. Что в вашем контуре бэкапа нарушает правило 3-2-1 и как это
   исправить в проде?
10. Зачем PostgreSQL параметр PGDATA в подкаталоге тома?
