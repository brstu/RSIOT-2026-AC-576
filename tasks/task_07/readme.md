# Лабораторная работа №7. IaC + CI/CD GitOps: Terraform/OpenTofu и Argo CD

**Дисциплина:** Распределённые системы и облачные технологии (РСиОТ)
**Тема:** стенд как код, конвейер GitHub Actions и автоматическая
доставка «СмартДома» через Argo CD

---

> 🚀 **Впервые здесь?** Начните с [QUICK_START.md](QUICK_START.md) —
> Terraform/OpenTofu + Argo CD в kind и первый автосинк за 30–40 минут.

---

## Цель работы

Собрать полный путь коммита без ручных шагов: описать стенд кодом
(Terraform или OpenTofu — на выбор), поднять Argo CD, отдать ему
манифесты «СмартДома» и построить конвейер GitHub Actions
`push → build → образ → бамп тега → автосинк` — а затем доказать
экспериментом, что self-heal возвращает кластер к git.

## Результаты обучения

После выполнения работы студент будет:

- уметь описывать ресурсы кластера HCL и работать по циклу
  `plan → review → apply`;
- уметь демонстрировать дрейф и его лечение (IaC и GitOps);
- уметь устанавливать Argo CD и описывать Application;
- строить конвейер CI: тесты → сборка образа → публикация в GHCR →
  обновление манифеста;
- объяснять pull-модель доставки и цену её отсутствия.

## Лекции-основы

- **Лекция 21.** IaC: HCL, plan/apply, state, drift, модули,
  Terraform/OpenTofu.
- **Лекция 22.** CI/CD и GitOps: конвейер, артефакты, push vs pull,
  Argo CD, progressive delivery.
- Пригодятся: лекция 18 (reconcile, Deployment), лаба 5 (сервис
  телеметрии и его образ).

## Теоретическая справка (кратко)

- **IaC:** источник истины — код; `plan` — дифф, `apply` — применение;
  ручные правки = дрейф, который apply снесёт.
- **GitOps (pull):** агент в кластере (Argo CD) тянет манифесты из git
  и непрерывно сверяет; ручной `kubectl` откатывается self-heal'ом;
  откат релиза = `git revert`.
- **Конвейер:** каждое изменение проходит одни и те же стадии; артефакт
  неизменяем, тег = SHA коммита.
- В лекции 22 показаны два репозитория (код + инфра); в лабе допускается
  **один репозиторий с каталогами `app/` и `infra/`** — принципы те же,
  а прав GITHUB_TOKEN хватает без PAT.

Полная теория — лекции 21–22 (`curriculum/`).

## Задание

Параметры (имя приложения, namespace, порт, реплики, инструмент IaC,
интервал теста) — по вашему варианту из [Варианты.md](Варианты.md).
Вариант 0 (эталон преподавателя) — в [examples/](examples/): копировать
1:1 нельзя.

### Часть 1. Быстрый первый успех: Argo CD и первый автосинк (30–40 минут)

1. Кластер: `kind create cluster --name smartdom` (если снесли).
2. Установите Argo CD по шагам QUICK_START, откройте UI.
3. Примените эталонный `examples/argocd/application.yaml` (указав свой
   fork) — Argo CD сам развернёт манифесты из `examples/infra/`.
4. Скриншот зелёного (Synced/Healthy) приложения в UI — точка опоры.

### Часть 2. Стенд кодом (лекция 21)

1. В каталоге `terraform/` опишите HCL'ем: namespace по варианту и
   базовые ресурсы стенда (как минимум ConfigMap с параметрами
   варианта; по желанию — установку Argo CD helm-провайдером).
2. Прогоните цикл: `init` → `plan` (сохраните вывод в отчёт!) →
   `apply` → повторный `plan` = `No changes`.
3. Эксперимент «дрейф»: измените ресурс руками (`kubectl edit/scale`),
   покажите, что `plan` видит расхождение, `apply` возвращает код.

### Часть 3. GitOps: Application и self-heal (лекция 22)

1. В своём репозитории создайте каталог `infra/` с манифестами вашего
   приложения (Deployment + Service из лабы 5, параметры — по варианту).
2. Опишите `Application` Argo CD на этот каталог с
   `syncPolicy.automated` + `selfHeal: true`.
3. Эксперимент «self-heal»: удалите Deployment руками — покажите
   скриншотами, что Argo CD вернул его за секунды; в UI видно событие.
4. Эксперимент «откат»: сделайте заведомо плохое изменение манифеста
   через git, затем `git revert` — покажите, что кластер вернулся.

### Часть 4. Конвейер: путь коммита без рук

1. Workflow GitHub Actions в `app/`: тесты → сборка образа → push в
   GHCR (`ghcr.io/<user>/<app>:<sha>`).
2. Финальный шаг workflow обновляет тег образа в `infra/deployment.yaml`
   (commit от бота в тот же репозиторий).
3. Прогоните полный путь: измените код (например, ответ эндпоинта) →
   push → дождитесь автосинка → покажите новую версию в кластере
   **без единой ручной команды kubectl**. Приложите скриншоты цепочки:
   зелёный workflow → коммит бота → Synced в Argo CD → ответ сервиса.

## Контрольные вопросы для защиты

1. Покажите в вашем plan-выводе, что и почему Terraform собирался
   создать/изменить.
2. Что произойдёт, если удалить ваш state-файл? Как восстановиться?
3. Чем ваш конвейер отличается от «kubectl apply из CI» и почему это
   важно?
4. Где в вашей схеме единственное место с человеком? Зачем оно там?
5. Покажите syncPolicy вашего Application. Что делает selfHeal?
6. Как выполняется откат релиза в вашей схеме? Продемонстрируйте.
7. Почему тег образа — SHA коммита, а не `latest`?
8. Какие права нужны вашему workflow и почему GITHUB_TOKEN хватает?
9. Что случится, если руками поменять образ в кластере? А в
   infra-каталоге без PR?
10. Как в вашу схему добавился бы canary (лекция 22)?
