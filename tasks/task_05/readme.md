# Лабораторная работа №5. Kubernetes: stateless-деплой сервиса «СмартДом»

**Дисциплина:** Распределённые системы и облачные технологии (РСиОТ)
**Тема:** Деплой stateless HTTP-сервиса в Kubernetes: Deployment, Service,
Ingress, ConfigMap/Secret, пробы, RollingUpdate

> установка kind/kubectl и первый работающий под за 30–40 минут.

## Цель работы

Развернуть stateless HTTP-сервис платформы «СмартДом» в локальном
Kubernetes-кластере: подготовить манифесты (Deployment, Service, Ingress,
ConfigMap/Secret), настроить пробы и ресурсы, выполнить обновление без
даунтайма и откат.

## Результаты обучения

После выполнения работы студент будет:

- уметь поднимать локальный кластер (kind/minikube) и работать с `kubectl`;
- уметь описывать Deployment с пробами, ресурсами и стратегией
  RollingUpdate;
- уметь публиковать сервис через Service (ClusterIP/NodePort) и Ingress;
- понимать, зачем конфигурация выносится в ConfigMap/Secret;
- применять `rollout status / history / undo` и объяснять, что происходит
  с ReplicaSet при обновлении.

## Лекции-основы

Работа опирается на лекции новой сетки 2026:

- **Лекция 16.** Облачные модели: managed K8s как PaaS, почему kind
  локально честно повторяет EKS/AKS/GKE.
- **Лекция 17.** Сетевые основы: Service = L4, Ingress = L7,
  сервис-дискавери = DNS.
- **Лекция 18.** Kubernetes основы: reconcile loop, матрёшка
  Pod → ReplicaSet → Deployment, пробы, requests/limits, RollingUpdate.

## Теоретическая справка (кратко)

- **Deployment** управляет ReplicaSet'ами и стратегией обновления
  (по умолчанию RollingUpdate: `maxUnavailable`/`maxSurge`); ReplicaSet
  держит N одинаковых подов живыми.
- **Service** даёт группе подов стабильное имя, виртуальный IP и
  DNS-запись; **Ingress** — L7-маршрутизация по хостам/путям, работает
  только при установленном Ingress Controller.
- **Пробы:** readiness — «слать ли трафик» (провал = под вне Service),
  liveness — «перезапустить ли» (проверяет только сам процесс!),
  startup — покрывает медленный старт.
- **requests/limits** — бронь для планировщика и потолок (OOMKill по
  памяти, троттлинг по CPU).

Полная теория — в лекциях 16–18 (`curriculum/`) и
[методических материалах](Лабораторная_работа_05_Методические_материалы.md)
(методичка 2025 года, сохранена как справочник).

## Задание

Сервис для деплоя — HTTP-сервис «СмартДома» **по вашему варианту** из
[Варианты.md](Варианты.md) (параметры: namespace, имя, порт, реплики,
ресурсы). За основу возьмите свой сервис из ЛР01 или готовый пример
приёма телеметрии из [examples/](examples/) (это вариант 0 — эталон;
копировать его 1:1 нельзя, параметры и логика — по варианту).

### Часть 1. Быстрый первый успех: кластер и первый под (30–40 минут)

1. Поднимите кластер: `kind create cluster --name smartdom`.
2. Задеплойте **готовый пример** из `examples/k8s/` командой
   `kubectl apply -f examples/k8s/` и убедитесь, что поды в `Running`,
   а `kubectl port-forward` отдаёт ответ сервиса.
3. Снимите скриншот `kubectl get pods -o wide` с работающими подами —
   это ваша точка опоры: кластер работает, дальше вы меняете только
   манифесты.

### Часть 2. Образ своего сервиса

1. Соберите образ сервиса по варианту с требованиями ЛР01: multi-stage,
   финальный образ ≤ 150 MB, non-root, graceful shutdown (SIGTERM),
   логирование старта/остановки.
2. Сервис обязан отдавать `GET /health/live` и `GET /health/ready` и
   логировать при старте `STU_ID`, `STU_GROUP`, `STU_VARIANT` из ENV.
3. Загрузите образ в кластер (`kind load docker-image <image>:<tag>`)
   или опубликуйте в GHCR/Docker Hub.

### Часть 3. Манифесты

Опишите в каталоге `k8s/` (значения — из вашего варианта):

1. `namespace.yaml` — ваш namespace.
2. `deployment.yaml` — реплики по варианту, `strategy: RollingUpdate`
   (`maxUnavailable: 0`, `maxSurge: 1`), requests/limits по варианту,
   readiness + liveness (liveness — только сам процесс!), метки и
   аннотации с метаданными (см. ниже).
3. `service.yaml` — ClusterIP (чётный вариант) или NodePort (нечётный).
4. `configmap.yaml` + `secret.yaml` — минимум по одному параметру,
   пробрасываемому в ENV (например, `ALERT_THRESHOLD_C` и
   `DB_PASSWORD`); значение секрета в git не коммитить открытым текстом
   в реальных проектах — здесь допускается учебная заглушка.
5. (Бонус) `ingress.yaml` — маршрут на ваш Service.

### Часть 4. Проверки и обновление без даунтайма

1. Smoke-тест: `kubectl port-forward` + запрос к сервису; проверьте
   `kubectl get endpoints` (готовые поды в списке).
2. Сломайте readiness (например, временно укажите неверный путь пробы) —
   покажите скриншотом, что под исключается из Endpoints; верните.
3. Обновите образ на новую версию (`kubectl set image`), проследите
   `rollout status`, затем выполните `rollout undo`. Зафиксируйте
   скриншотами смену ReplicaSet'ов (`kubectl get rs`).

## Контрольные вопросы для защиты

1. Что произойдёт, если удалить под вашего Deployment командой
   `kubectl delete pod`? Почему?
2. Чем ReplicaSet отличается от Deployment и зачем оба?
3. Покажите в ваших манифестах, где selector, а где labels — что будет
   при их несовпадении?
4. Почему liveness-проба не должна проверять базу данных?
5. Что показывает `kubectl get endpoints` и почему список может быть
   пустым?
6. Как RollingUpdate с `maxUnavailable: 0` обеспечивает ноль даунтайма?
7. Чем ClusterIP отличается от NodePort? Когда нужен LoadBalancer?
8. Почему Secret — это не шифрование? Что было бы правильно в проде?
9. Что случится с вашим подом при превышении limit памяти? CPU?
10. Зачем в манифестах метки `org.bstu.*`?
