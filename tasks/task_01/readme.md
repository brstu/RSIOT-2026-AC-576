## 🚀 Быстрый первый успех (15 минут)

Прежде чем писать свой сервис — запустите готовый пример и убедитесь,
что окружение работает. Все команды — PowerShell, копируются построчно.

```powershell
# 1. Проверка окружения (Docker Desktop должен быть запущен)
docker version
docker compose version

# 2. Перейти в папку примера (внутри клона репозитория курса)
cd tasks\task_01\examples

# 3. Поднять стенд: сервис телеметрии + Redis
docker compose up --build -d

# 4. Отправить показание датчика (сущность Reading из лекции 01)
Invoke-RestMethod -Method Post -Uri http://localhost:8080/readings -ContentType "application/json" -Body '{"device_id":"dev-42","sensor":"temperature","value":21.5}'

# 5. Прочитать показания устройства
Invoke-RestMethod http://localhost:8080/devices/dev-42/readings

# 6. Убедиться, что HEALTHCHECK зелёный (STATUS = healthy).
#    Сразу после старта будет health: starting — подождите ~15 секунд и повторите
docker compose ps

# 7. Погасить стенд
docker compose down
```

Если шаг 4 вернул JSON с `"accepted": true` — окружение готово, вы уже
запустили контейнеризованный сервис «СмартДома». Дальше делаете то же самое,
но своими руками и под свой вариант.

⚠️ Типичные проблемы на этом шаге:

* `error during connect ... pipe/dockerDesktopLinuxEngine` — Docker Desktop не запущен; запустите его и дождитесь зелёного кита.
* Порт 8080 занят — остановите занявший его процесс или поменяйте левую часть `ports:` в `compose.yaml` (например, `8081:8080`).
* Корпоративный прокси/VPN мешает `docker pull` — проверьте настройки прокси в Docker Desktop.

## Теоретическая справка (кратко)

Полная теория — в [лекции 02](../../curriculum/Лекция_02_Контейнеры.md). Минимум для лабы:

* **Контейнер — процесс хоста с изоляцией** (namespaces + cgroups + слои union FS), а не «лёгкая виртуалка»: ядро общее, своей гостевой ОС нет.
* **Образ** — стопка read-only слоёв; порядок инструкций Dockerfile управляет кэшем: зависимости (`requirements.txt` / `package.json`) копируются и ставятся **до** кода.
* **Writable-слой умирает вместе с контейнером** — состояние живёт в volume.
* **Тег — изменяемая метка** (`latest` — просто дефолт), неизменяемость даёт только digest `sha256:...` (кейс компрометации Trivy, март 2026 — перезаписали даже `latest`).
* **EXPOSE — документация**; порт публикует `-p` / `ports:`.
* **HEALTHCHECK** — exec-форма без `curl` (в slim-образах его нет).
* **Compose v2**: команда `docker compose` (через пробел), канонический файл — `compose.yaml`, поле `version:` устарело; `depends_on` — порядок старта, **не** готовность → сервис обязан переживать недоступность зависимости (ретраи из лекции 01).

## Задание

Параметры (стек, сущности, эндпоинты, порт, зависимость, UID, тег) — по вашему
варианту из [Варианты.md](./Варианты.md). Студенты набора 2026 берут варианты
46–70 («СмартДом»); варианты 1–45 сохранены для пересдач прошлых лет.

### Часть 1. Сервис «СмартДома» (каркас)

Напишите минимальный HTTP-сервис на стеке варианта (Python 3.12/FastAPI или
Node.js 22) с эндпоинтами варианта (например, `POST /readings`,
`GET /devices/{id}/readings`) и health-эндпоинтом. Требования:

* конфигурация только через переменные окружения (порт, адрес зависимости, `STU_ID`, `STU_VARIANT` — логируются при старте);
* данные храните в зависимости варианта (Redis или PostgreSQL), не в памяти процесса и не в файлах контейнера;
* при недоступности зависимости сервис не падает: отвечает 503 на health и повторяет подключение (лекция 01 — частичный отказ, а не полный).

### Часть 2. Dockerfile

* Multi-stage: стадия сборки зависимостей отдельно от финальной; финальный образ ≤ 150 МБ;
* порядок слоёв использует кэш: файл зависимостей копируется до исходников;
* `USER` — непривилегированный, числовой UID из варианта;
* `HEALTHCHECK` в exec-форме (без `curl`), проверяет health-эндпоинт варианта;
* `EXPOSE` соответствует порту варианта; `.dockerignore` исключает мусор (`.git`, `node_modules`, `__pycache__`, логи, секреты);
* LABEL с метаданными студента (см. ниже).

### Часть 3. Docker Compose

* Файл `compose.yaml` (без поля `version:`): ваш сервис + зависимость (Redis/PostgreSQL по варианту);
* именованный volume для данных зависимости (имя — по варианту);
* переменные окружения сервиса задаются в compose; секретов в Dockerfile нет;
* `healthcheck` у зависимости и `depends_on` с `condition: service_healthy`;
* labels на сервисах (см. метаданные).

### Часть 4. Graceful shutdown и проверка

* Сервис корректно завершается по SIGTERM (лог о завершении, соединения закрыты);
* продемонстрируйте: `docker compose stop` → в логах видно graceful-завершение, код выхода 0 (`docker compose ps -a`);
* соберите логи старта (с `STU_*`), обработки запросов и завершения — в отчёт.

### Часть 5. Кэш сборки

* Покажите (скриншотами/логами двух сборок), что при изменении только кода слои зависимостей берутся из кэша (`CACHED`), а при изменении файла зависимостей — пересобираются.

## Метаданные студента (обязательно)

В README своего проекта: StudentID, GitHub username, № варианта, дата,
версия ОС и Docker Desktop/Engine (без ФИО, группы и email).

В Dockerfile → `LABEL`:

* `org.bstu.student.id` = StudentID
* `org.bstu.variant` = номер варианта
* `org.bstu.course` = RSIOT

В `compose.yaml` → `labels` на сервисах:

* `org.bstu.owner` = GitHub username
* `org.bstu.student.slug` = slug

slug = `<StudentID>-v<вариант>` (например, `12345-v47`).

## Требования к именованию

* Теги образов: суффикс `:stu-<StudentID>-v<вариант>`; тег `latest` не использовать;
* имена контейнеров/томов/сетей включают slug (`app-<slug>`, `data-<slug>`, `net-<slug>`);
* ENV `STU_ID`, `STU_VARIANT` — логируются при старте;
* PostgreSQL: имя БД `app_<StudentID>_v<вариант>`; Redis: префикс ключей `stu:<StudentID>:v<вариант>:<entity>`.

## Зачем в реальных системах

| Что делаете в лабе | Где это в производстве |
| --- | --- |
| Multi-stage и минимальный образ | Меньше поверхность атаки и трафик реестра; быстрее старт под автоскейлингом; в проде «цех» (компиляторы, dev-зависимости) в витрину не попадает |
| Non-root USER | Стандарт безопасности: побег из контейнера под root = root-процесс на хосте; кластеры (Pod Security Standards) просто не пустят root-образ в прод |
| HEALTHCHECK | Оркестратор (лаба 2 — Kubernetes) перезапускает и выводит из балансировки нездоровые экземпляры автоматически — без него «зомби-процесс» принимает трафик |
| Volume для данных | Контейнеры в проде пересоздаются десятки раз в день (деплой, автоскейлинг, миграция узлов) — данные обязаны это переживать |
| Graceful shutdown | При каждом деплое оркестратор шлёт SIGTERM; кто не завершился корректно — теряет незаписанные Reading и рвёт запросы жильцов |
| Ретраи к зависимости | Порядок старта в проде не гарантирован (лекция 01: сеть ненадёжна); сервис, падающий без БД, роняет каскадом весь стенд |
| LABEL/метаданные | По меткам в компании находят владельца образа при инциденте 03:00 ночи; FinOps считает по ним стоимость |
