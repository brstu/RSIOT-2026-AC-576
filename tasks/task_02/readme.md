# Лабораторная работа №2. Взаимодействие сервисов: REST, идемпотентность, ретраи

**Дисциплина:** Распределённые системы и облачные технологии (РСиОТ)
**Тема:** надёжный межсервисный вызов: таймауты, ретраи с backoff и джиттером, ключ идемпотентности, retry storm

---

## Цель работы

Разделить «СмартДом» на два сервиса и сделать вызов между ними надёжным:
таймауты на клиенте, ретраи с экспоненциальным backoff и джиттером, ключ
идемпотентности против дублей — и показать экспериментом, что ретраи без
джиттера превращаются в retry storm.

После выполнения работы студент будет:

## 🚀 Быстрый первый успех (15 минут)

Пример из [examples/](examples/) **сломан из коробки — так задумано**: ключ
идемпотентности выключен, а первый ответ сервиса тревог «теряется» в сети.
Поднимите стенд и увидите дубль тревоги своими глазами. Все команды —
PowerShell, копируются построчно.

```powershell
# 1. Проверка окружения (Docker Desktop должен быть запущен)
docker version

# 2. Перейти в папку примера (внутри клона репозитория курса)
cd tasks\task_02\examples

# 3. Поднять оба сервиса: devices (приём показаний) + alerts (тревоги)
docker compose up --build -d

# 4. Убедиться, что оба контейнера healthy (иначе подождите ~10 секунд и повторите)
docker compose ps

# 5. Отправить ОДНО показание выше порога 60.0 — devices вызовет alerts
Invoke-RestMethod -Method Post -Uri http://localhost:8080/readings -ContentType "application/json" -Body '{"device_id":"dev-7","sensor":"temperature","value":72.5}'

# 6. Посмотреть тревоги: показание одно, а тревог... ДВЕ. Это дубль!
Invoke-RestMethod http://localhost:8081/alerts
```

В ответе шага 5 видно, что было: `attempt 1: ReadTimeout` → пауза →
`attempt 2: HTTP 201`. Первый ответ alerts потерялся, клиент повторил
запрос — и alerts честно создал **вторую** тревогу. Жильцу придут два
уведомления о пожаре. Теперь почините это одним флагом:

```powershell
# 7. Включить ключ идемпотентности и пересоздать devices
$env:IDEMPOTENCY = "on"
docker compose up -d devices

# 8. Ещё одно показание выше порога
Invoke-RestMethod -Method Post -Uri http://localhost:8080/readings -ContentType "application/json" -Body '{"device_id":"dev-7","sensor":"temperature","value":80.1}'

# 9. Тревог стало на ОДНУ больше, хотя попыток снова две (в ответе шага 8 — replayed=true)
Invoke-RestMethod http://localhost:8081/alerts
```

Если после шага 6 тревог две, а после шага 9 добавилась только одна —
вы воспроизвели главную проблему лабы и её решение. Дальше делаете то же
самое своими руками под свой вариант.

⚠️ Типичные проблемы на этом шаге:

* `error during connect ... pipe/dockerDesktopLinuxEngine` — Docker Desktop не запущен; запустите его и дождитесь зелёного кита.
* Порт 8080 или 8081 занят — поменяйте левую часть `ports:` в `compose.yaml` (например, `18080:8080`) и подставьте новый порт в команды.
* «Почему всегда две попытки?» — флаг `SIMULATE_LOST_RESPONSE=on` детерминированно «теряет» первый ответ, чтобы обрыв воспроизводился на каждом запросе, а не раз в неделю.

## Теоретическая справка (кратко)

Полная теория — в [лекции 03](../../curriculum/Лекция_03_Взаимодействие_в_распределенных_системах.md),
справочник с формулами и кодами ответов — в [методических материалах](./Лабораторная_работа_02_Методические_материалы.md).
Минимум для лабы:

* **У сетевого вызова три исхода:** успех, ошибка и **«неизвестно»** — ответ не пришёл, но сервер МОГ обработать запрос. Повтор в состоянии «неизвестно» без ключа идемпотентности = возможный дубль.
* **Таймаут обязателен** и выбирается по p99 задержки вызываемого сервиса, а не «30 секунд на всякий случай».
* **Ретраить можно** сетевые ошибки, таймауты и 5xx; **нельзя** — 4xx (запрос сломан, повтор не поможет).
* **Пауза между попытками:** `delay = min(cap, base * 2^attempt)`, спать `random(0, delay)` — full jitter. Без джиттера все клиенты возвращаются синхронной волной (retry storm).
* **Ключ идемпотентности** генерирует клиент **до первой попытки**, один на всю операцию; сервер хранит «ключ → ответ» атомарно с эффектом и на повтор отдаёт сохранённый ответ.
* **Ретраит один слой** цепочки, иначе попытки перемножаются (retry amplification).

### Часть 1. Два сервиса и «сломанный» вызов

Напишите два HTTP-сервиса на стеке варианта (Python 3.12/FastAPI или
Node.js 22): **вызывающий** (caller) и **принимающий** (callee). Эндпоинт
callee из варианта — POST, создающий запись (операция неидемпотентна по
природе). Требования:

* оба сервиса — в одном `compose.yaml`, обращение по DNS-имени сервиса; health-эндпоинты; конфигурация через переменные окружения (`STU_ID`, `STU_GROUP`, `STU_VARIANT` логируются при старте);
* встройте имитацию сбоя из варианта (потеря ответа / окно 503 / отказ до обработки) — управляемую переменной окружения или служебным эндпоинтом;
* **воспроизведите дубль**: один запрос к caller → две записи в callee. Сохраните вывод/скриншот — это артефакт «до».

### Часть 2. Таймауты

* На клиенте caller задайте connect- и read-таймауты (значения — через переменные окружения);
* обоснуйте значения в отчёте: почему именно столько, что случится при большем/меньшем;
* покажите логом, что зависший вызов обрывается по таймауту, а не висит вечно.

### Часть 3. Ретраи с backoff и джиттером

* Повторяйте **только** сетевые ошибки, таймауты и 5xx; 4xx не повторяются — докажите логом: одна попытка на 4xx-ответ (проще всего временно отправить заведомо некорректное тело — FastAPI/валидатор callee ответит 422);
* экспоненциальный backoff с **full jitter** и потолком паузы (`base`, `cap` — конфигурируемы), потолок числа попыток;
* джиттер включается/выключается флагом (нужно для части 5);
* лог каждой попытки: номер, исход, длительность паузы.

### Часть 4. Ключ идемпотентности

* Клиент генерирует `Idempotency-Key` **до первой попытки**, один на все попытки операции;
* callee хранит «ключ → сохранённый ответ» (память процесса или Redis — по варианту) и на повтор возвращает **первый** ответ с маркер-заголовком (например, `Idempotency-Replayed: true`), не создавая запись;
* проверка ключа и запись эффекта не должны разрываться (см. методичку — атомарность);
* **повторите сценарий части 1 с ключом**: дубля нет. Сохраните вывод/скриншот — артефакт «после».

### Часть 5. Эксперимент retry storm

* Напишите скрипт: не менее 20 параллельных клиентов бьют в callee, у которого включено окно отказа (несколько секунд все запросы → 503);
* скрипт собирает время каждой попытки и печатает распределение запросов по времени (гистограмма или счётчики по окнам);
* два прогона: джиттер выключен / включён; сравните **пиковое число запросов в одно окно времени** и сделайте вывод в отчёте;
* логи обоих прогонов — обязательный артефакт (`logs/retry_storm_off.txt`, `logs/retry_storm_on.txt`).

## Бонусы (+ до 15)

* **429 и Retry-After** (+5) — в окне отказа callee отвечает `429`/`503` с заголовком `Retry-After`; клиент уважает его вместо собственного backoff; разница видна в логах.
* **Дедлайн по цепочке** (+4) — caller передаёт бюджет времени (например, заголовок `X-Deadline`); клиент не начинает новую попытку, если бюджета не хватает; callee отклоняет запросы с истёкшим дедлайном.
* **Конфликт тел** (+3) — повтор с тем же `Idempotency-Key`, но другим телом → `422` (семантика Stripe): ключ привязан к операции, а не к URL.
* **Метрики попыток** (+3) — эндпоинт `/metrics` у caller: счётчики попыток, ретраев и replay-ответов; значения после экспериментов — в отчёте.

## Зачем в реальных системах

| Что делаете в лабе | Где это в производстве |
| --- | --- |
| Таймауты на клиенте | Любой прод-вызов имеет бюджет времени; без таймаута один зависший сервис держит соединения и валит всю цепочку каскадом |
| Backoff + джиттер | Встроены в AWS SDK, gRPC и Kubernetes; сбой Google Cloud 12.06.2025 затянулся на лишние часы именно из-за перезапусков без рандомизированного backoff |
| Ключ идемпотентности | Stripe/PayPal: повтор платёжного POST без ключа = двойное списание; API-платежи без Idempotency-Key в проде не живут |
| Ретраит один слой | Три слоя по 4 попытки = до 64 запросов на один пользовательский клик (retry amplification) — так «немного ретраев» добивает лежащий сервис |
| Окно отказа + 503 | Осознанный отказ (load shedding) дешевле зависания: клиенту сразу ясно «повтори позже», а сервис не копит очередь |
| Эксперимент со сбоем | То, что вы делали руками, в проде делает chaos engineering (лекция 9): сбои впрыскивают специально, чтобы проверить надёжность до инцидента |

## Контрольные вопросы для защиты

1. Чем сетевой вызов отличается от локального? Назовите три исхода сетевого вызова.
2. Почему таймаут — это не ответ «нет»? Что мог успеть сделать сервер к моменту таймаута?
3. Как вы выбрали значение read-таймаута? Чем плохи и «слишком мало», и «30 секунд на всякий случай»?
4. Какие ответы ваш клиент повторяет, а какие нет? Почему повторять 4xx бессмысленно?
5. Напишите формулу backoff с full jitter и объясните роль `base`, `cap` и случайности. Покажите на своих гистограммах, что даёт джиттер.
6. Что такое retry storm и retry amplification? Почему ретраить должен один слой цепочки?
7. Кто и когда генерирует Idempotency-Key? Почему «новый ключ на каждую попытку» — классическая ошибка?
8. Что ваш callee хранит по ключу и почему запись ключа должна быть атомарной с эффектом? Зачем ключам TTL?
9. Что вернёт ваш callee при повторе с тем же ключом? А при том же ключе, но другом теле запроса?
10. Почему exactly-once delivery невозможна и как at-least-once + дедупликация дают exactly-once processing?
