## 1. Модель сбоя: три исхода вызова

У локального вызова два исхода: вернулся или упал. У сетевого — три:

1. **Успех** — ответ пришёл.
2. **Ошибка** — пришёл ответ «не получилось» (4xx/5xx).
3. **«Неизвестно»** — ответа нет. Запрос мог потеряться ДО сервера
   (безопасно повторять) или ПОСЛЕ обработки (повтор = дубль). Снаружи эти
   случаи неразличимы — поэтому повтор POST без ключа идемпотентности всегда
   риск дубля.

Пример лабы это воспроизводит честно: alerts создаёт тревогу и «теряет»
ответ — клиент видит таймаут, хотя эффект уже случился.

## 2. Таймауты

### Python: httpx

```python
import httpx

# По умолчанию у httpx таймаут 5 с на всё. Задавайте явно и раздельно:
timeout = httpx.Timeout(
    connect=1.0,   # установить TCP-соединение
    read=0.8,      # ждать ответ после отправки запроса
    write=1.0,     # отправить тело
    pool=1.0,      # дождаться свободного соединения из пула
)
async with httpx.AsyncClient(timeout=timeout) as client:
    resp = await client.post(url, json=payload)
```

`read` — главный: столько вы готовы ждать ответ. Истёк — исключение
`httpx.ReadTimeout` (подкласс `httpx.TransportError`).

### Node.js 22: fetch + AbortSignal

```js
// Встроенный fetch отменяется через AbortSignal.timeout (миллисекунды!)
try {
  const resp = await fetch(url, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(800),   // 0.8 c на весь запрос
  });
} catch (err) {
  if (err.name === "TimeoutError") { /* таймаут — кандидат на ретрай */ }
}
```

### Как выбирать значение

* Ориентир — **p99 задержки вызываемого сервиса** плюс запас, а не «круглое число». Для локального стенда измерьте сами (см. § 7).
* Слишком маленький таймаут — ретраи на здоровом сервисе (ложные дубли нагрузки); слишком большой — зависшие вызовы копятся и съедают соединения/память, отказ каскадом ползёт вверх по цепочке.

## 3. Ретраи: что повторять и как ждать

**Повторять:** сетевые ошибки (connect refused, reset), таймауты, `5xx`,
`429` (но с уважением к `Retry-After`, см. § 5).
**Не повторять:** остальные `4xx` — запрос сломан, повтор даст тот же ответ
и лишнюю нагрузку.

Формула паузы перед попыткой `n` (n = 1, 2, ...) — экспоненциальный backoff
с **full jitter** (рекомендация AWS):

```text
delay = min(cap, base * 2^(n-1))     # экспонента с потолком
sleep = random(0, delay)             # full jitter: случайная точка в [0, delay]
```

```python
import random

def backoff_delay(attempt: int, base: float = 0.2, cap: float = 2.0) -> float:
    return random.uniform(0.0, min(cap, base * 2 ** (attempt - 1)))
```

Зачем каждая часть:

* **экспонента** — нагрузка на болеющий сервис падает с каждой попыткой;
* **cap** — чтобы паузы не росли до минут;
* **джиттер** — рассинхронизирует клиентов. Без него все, кто получил отказ
  одновременно, вернутся одновременно — волна за волной (retry storm).
  Именно это вы измеряете в части 5;
* **потолок попыток** — ретраи не бесконечны; исчерпали — отдаёте ошибку
  вверх.

**Retry amplification:** если ретраит каждый слой цепочки A → B → C по 4
попытки, один клик пользователя превращается в до 16 запросов к C. Правило:
ретраит **один** слой (обычно ближайший к источнику отказа), остальные
быстро отдают ошибку наверх.

## 4. Ключ идемпотентности

Семантика (так работает Stripe; черновик стандарта IETF —
`Idempotency-Key` header):

1. **Клиент** генерирует ключ (UUID) **до первой попытки** — один на всю
   операцию, во все повторы уходит тот же ключ. Новый ключ = новая операция.
2. **Сервер** на первый запрос выполняет эффект и сохраняет пару
   «ключ → ответ (статус + тело)». Запись ключа должна быть **атомарной с
   эффектом**: между «проверил, что ключа нет» и «записал ключ» не должен
   вклиниться параллельный запрос-близнец.
3. На повтор с известным ключом сервер **не выполняет эффект**, а возвращает
   сохранённый ответ (полезно пометить заголовком, например
   `Idempotency-Replayed: true`).
4. Ключи хранятся с **TTL** (Stripe — 24 часа): вечное хранилище ключей —
   утечка памяти.
5. Повтор с тем же ключом, но **другим телом** — ошибка клиента: `422`.

Хранилища в лабе:

* **Память процесса** (dict в Python, Map в Node): годится при одном
  процессе; в asyncio проверка+эффект+запись без `await` между ними —
  атомарны. Честно отметьте в отчёте ограничение: второй воркер или
  перезапуск — и ключи потеряны.
* **Redis:** атомарность даёт `SET key value NX EX 86400` — запись «только
  если ключа нет» плюс TTL одной командой; вернул `nil` — ключ уже есть,
  берите сохранённый ответ (`GET`).

## 5. Коды ответов, которые понадобятся

| Код | Смысл | В этой лабе |
| --- | --- | --- |
| `201 Created` | Запись создана | Успех POST callee (и replay сохранённого ответа) |
| `409 Conflict` | Конфликт состояния ресурса | Повтор с ключом, обработка которого ещё идёт (первый запрос не завершился) |
| `422 Unprocessable Content` | Запрос синтаксически верен, семантически — нет | Тот же ключ, другое тело (бонус); ретраить нельзя |
| `425 Too Early` | Сервер не готов рисковать повтором | Редкий; знать, что существует именно для early-data повторов |
| `429 Too Many Requests` | Клиент слишком част | Лимитирование; повторять только после `Retry-After` |
| `503 Service Unavailable` | Сервису плохо, но это временно | Окно отказа; безопасен для ретрая — эффекта не было |
| `Retry-After: N` | Заголовок к 429/503: повторяй через N секунд | Бонус: клиент подчиняется серверу вместо своего backoff |

## 6. Типичные ошибки

1. **Новый Idempotency-Key на каждую попытку.** Сервер видит «новые»
   операции — дубли возвращаются. Ключ генерируется до первой попытки и
   живёт все попытки.
2. **Ретрай 4xx.** 400/404/422 не лечатся повтором. Ретрай по «любой
   ошибке» — антипаттерн курса № 1.
3. **Backoff без джиттера.** Работает на одном клиенте, а на 30 даёт волны —
   ваша же гистограмма из части 5 это докажет.
4. **Проверка ключа и эффект разорваны.** `if key not in store:` → `await
   что-нибудь` → запись: в зазор влезает близнец-запрос, дубль создан.
   В asyncio держите проверку+эффект+запись без `await` между ними; в Redis
   используйте `SET NX`.
5. **Таймаут только на connect.** Соединение установилось, а ответа нет —
   вызов висит вечно. Обязателен read-таймаут.
6. **Ретраи на каждом слое.** Амплификация: см. § 3. В лабе ретраит только
   клиент caller.
7. **`depends_on` вместо готовности.** Из ЛР1: порядок старта ≠ готовность;
   caller обязан переживать недоступность callee (503/ретраи, не падение).

## 7. Отладка в PowerShell (Windows)

Команды рассчитаны на Windows PowerShell 5.1 (без `&&`, без
`-SkipHttpErrorCheck`).

```powershell
# Заголовки и статус ответа (curl.exe, НЕ алиас curl!):
curl.exe -i http://localhost:8081/alerts

# POST с заголовком Idempotency-Key вручную — повторите дважды и сравните:
curl.exe -i -X POST http://localhost:8401/your-endpoint -H "Content-Type: application/json" -H "Idempotency-Key: test-123" -d '{\"device_id\":\"dev-1\"}'

# Invoke-RestMethod на 4xx/5xx кидает исключение; статус достаём так:
try { Invoke-RestMethod http://localhost:8081/alerts -Method Post } catch { $_.Exception.Response.StatusCode.value__ }

# Замерить задержку вызова (для обоснования таймаута):
Measure-Command { Invoke-RestMethod http://localhost:8081/health } | Select-Object TotalMilliseconds

# Логи сервисов в реальном времени (в отдельном окне):
docker compose logs -f devices
docker compose logs -f alerts

# Пересоздать один сервис после смены переменной окружения:
$env:IDEMPOTENCY = "on"
docker compose up -d devices

# Вывести лог эксперимента в файл для отчёта:
docker compose exec devices python -m app.retry_storm --clients 30 --outage 3 --jitter off | Tee-Object -FilePath logs\retry_storm_off.txt
```

⚠️ `curl` без `.exe` в PowerShell 5.1 — алиас `Invoke-WebRequest` с другими
параметрами; всегда пишите `curl.exe`. Одинарные кавычки вокруг JSON-тела в
`curl.exe` не работают как в bash — экранируйте внутренние кавычки `\"` (см.
пример выше) или используйте `Invoke-RestMethod -Body '{"a":1}'`.
