## Крючок: ваш банк делает event sourcing уже пятьсот лет

> 🖥 **Слайд 2.** Крючок: гроссбух и Git

Спросите себя: хранит ли банк ваш баланс? Нет. Банк хранит **проводки** —
неизменяемый журнал операций, а баланс **вычисляется** из журнала.
Бухгалтерская книга с двойной записью — практика с XV века: запись нельзя
стереть, ошибку исправляет новая корректирующая запись, и любой аудитор
может восстановить состояние счёта на любую дату. Современные финтехи
описывают свой ledger теми же словами: «event-sourced запись всех
изменений баланса».

И второй пример — у каждого из вас на ноутбуке. **Git**: commit — событие,
ветка — проекция, `git checkout <hash>` — реконструкция состояния проекта
на момент времени. Вы пользуетесь event sourcing ежедневно — просто не
называли его так.

Вопрос залу: **почему банк и Git хранят историю изменений, а типичная
CRUD-таблица `devices` — только последнее состояние? Что мы теряем при
UPDATE?**

Держите ответ: к середине пары «потерянное при UPDATE» получит имя, цену

## Картина мира: фотография против киноплёнки

> 🖥 **Слайд 5.** Дорожная карта пары

Обычная база данных — фотография: снимок «как сейчас». UPDATE перерисовал
кадр, старого больше нет. Журнал событий — киноплёнка: каждый кадр
неизменен, «сейчас» — это просто последний кадр, а прокрутив плёнку, вы
увидите, **как** система пришла в текущее состояние и **что происходило**
по дороге.

Прошлые пары дали всю механику: журнал с реплеем (лекция 12), надёжную
публикацию событий (outbox, лекция 11), дедупликацию (идемпотентный
потребитель). Сегодня меняем точку зрения: события — не побочный продукт
изменения состояния, а **само состояние**. Таблица становится производной,
кэшируемой, пересоздаваемой — как ветка в Git.

Маршрут: событие против команды → три топологии интеграции → event
sourcing и агрегаты → живой сеанс с термостатом → снапшоты и версии →
CQRS без мифов → жизнь с отстающей read-моделью → когда всё это не нужно.
Два квиза, одно голосование, один живой сеанс.

## Основные понятия

**Определения** (пополним глоссарий в конце):

- **Событие** — неизменяемый свершившийся факт, названный в прошедшем
  времени: `TargetTemperatureSet`. Не просьба и не приказ.
- **Команда** — просьба сделать: `SetTargetTemperature`. Может быть
  отклонена; событие — уже нет, оно случилось.
- **Агрегат** — сущность, чьи события образуют один упорядоченный поток
  (термостат dev-17); граница транзакционной согласованности.
- **Проекция (read-модель)** — производное представление, построенное
  из событий под конкретные запросы.
- **Снапшот** — сохранённое состояние агрегата на момент N, чтобы не
  реплеить всю историю.

## Ядро пары

### 1. Событие против команды: грамматика архитектуры

> 🖥 **Слайд 6.** Событие ≠ команда

Разница не косметическая:

- **Команда** адресована конкретному исполнителю, ждёт решения и может
  быть отклонена: «списать оплату». Связывает отправителя с получателем.
- **Событие** — анонимная публикация факта: «оплата списана». Издатель
  не знает и не должен знать, кто слушает; подписчиков может быть ноль
  или двадцать.

Антипаттерн — **командное событие**: `SendWelcomeEmailEvent` в топике.
Формально событие, по сути приказ конкретному сервису — связность
вернулась, только теперь она асинхронная и хуже отлаживается. Тест
простой: **событие называется в прошедшем времени и остаётся истинным
навсегда**. `UserRegistered` — истина навсегда; «отправь письмо» — не
факт, а желание.

Каждому событию — конверт (лекции 11–12 уже дали всё необходимое):
`event_id` (для дедупликации), `schema_version` (для эволюции через
реестр схем), `ts`, тип и payload.

### 2. Три топологии: сколько данных везёт событие

> 🖥 **Слайд 7.** Три топологии

Событийная интеграция бывает трёх сортов — по количеству данных в событии:

1. **Уведомление (notification).** «Устройство dev-17 обновилось» + ссылка.
   Потребитель идёт за деталями сам, синхронным запросом. Событие тощее,
   но интеграция наполовину синхронная: издатель должен быть доступен
   для обратных запросов — та самая «скрытая синхронность».
2. **Event-carried state transfer.** Событие везёт данные с собой:
   `DeviceUpdated{полное состояние}`. Потребители строят локальные копии
   и не дёргают издателя вовсе. Цена — дублирование данных и вопросы
   их свежести.
3. **Event sourcing.** События — не сообщения О изменении состояния,
   а **само хранение** состояния. Дальше — подробно.

Первые две — про интеграцию МЕЖДУ сервисами; третья — про устройство
хранения ВНУТРИ сервиса. Их часто путают: можно делать event sourcing
внутри и публиковать наружу лишь уведомления — и наоборот.

### 3. Event sourcing: журнал — истина, таблица — кэш

> 🖥 **Слайд 8.** Event sourcing

Механика на агрегате «термостат dev-17»:

- Всякое изменение — **append** события в поток агрегата:
  `DeviceRegistered`, `TargetTemperatureSet{21}`,
  `TargetTemperatureSet{23}`, `EcoModeEnabled`.
- Текущее состояние — **свёртка** (fold) событий слева направо: применили
  все — получили «уставка 23, эко включён». Никакого UPDATE — только
  чтение журнала.
- Команда обрабатывается так: загрузить события агрегата → восстановить
  состояние → проверить инварианты (уставка в допустимом диапазоне?) →
  **дописать** новое событие. Конфликт двух одновременных команд ловится
  оптимистичной блокировкой по номеру версии потока.

Что это даёт — и это ответ на вопрос крючка, «что мы теряем при UPDATE»:

- **Аудит бесплатно**: кто, когда и что менял — не отдельная таблица
  логов (которую забыли обновить), а сама суть хранения.
- **Отладка машиной времени**: реплей событий до момента T воспроизводит
  состояние системы в момент бага.
- **Новые вопросы к старым данным**: «сколько раз жильцы меняли уставку
  вручную после срабатывания правила?» — реплей истории отвечает на
  вопрос, который никто не задавал при проектировании.

Хранить потоки можно в специализированной БД (KurrentDB — бывший
EventStoreDB), поверх PostgreSQL или в Kafka; принципиально одно:
append-only и чтение потока по порядку.

### 4. Живой сеанс: термостат на киноплёнке

> 🖥 **Слайд 9.** Живой сеанс

Строим вместе (7–10 минут), на доске — таблица-журнал. Ход мысли важнее
нотации.

**Шаг 1 — пишем историю.** Жилец у нас на глазах крутит термостат:

| # | Событие | Данные |
| --- | --- | --- |
| 1 | DeviceRegistered | dev-17, спальня |
| 2 | TargetTemperatureSet | 21°, кто: жилец u-7 |
| 3 | RuleTriggered | правило «ночь»: уставка 19° |
| 4 | TargetTemperatureSet | 23°, кто: жилец u-7 |

**Шаг 2 — реконструкция.** Спрашиваем зал: какая уставка сейчас?
Сворачиваем события: 23°. Проговариваем: мы только что «выполнили
SELECT» чтением журнала.

**Шаг 3 — проекция.** Панели жильца нужен мгновенный ответ, а не свёртка
на каждый запрос. Строим read-модель `current_settings(device_id, target,
eco)` — маленький потребитель читает поток и обновляет табличку. Упала?
Удаляем и **пересоздаём реплеем** — это тот самый реплей из лекции 12,
только теперь он пересоздаёт данные.

**Шаг 4 — вопрос аудитора.** «3 января в 02:00 отопление жарило на 23°.
Почему?» Журнал отвечает: событие № 4, жилец u-7, вчера в 23:47, вручную
перебил ночное правило. CRUD-таблица ответила бы молчанием: у неё есть
только «сейчас».

**Пояснение к примеру:** обратите внимание на событие № 3 — правило
записано С ПРИЧИНОЙ (`RuleTriggered`), а не как безликое изменение поля.
Проектирование событий = проектирование словаря предметной области.

**Проверка:** попросите соседа назвать состояние после первых трёх
событий (уставка 19°, эко нет) — если ответы сходятся, свёртка понята.

Типичные ошибки:

1. События-«изменения полей» (`FieldChanged{field, value}`) вместо
   доменных фактов — журнал есть, а смысла в нём нет.
2. Мутировать прошлое событие «для исправления» — только новое
   корректирующее событие (как сторно в бухгалтерии).
3. Один поток на всю систему вместо потока на агрегат — конфликты
   версий и реплей на годы.

### 5. Снапшоты и версии событий: цена вечной памяти

> 🖥 **Слайд 10.** Снапшоты и версии

Два вопроса, которые задаёт каждый, увидев event sourcing впервые:

**«Реплеить тысячи событий на каждую команду?»** Нет — **снапшот**:
периодически сохраняем свёрнутое состояние агрегата («на событии № 500
состояние такое»), и реконструкция = снапшот + хвост событий после него.
Снапшот — оптимизация, не истина: его можно стереть и пересчитать.

**«А если схема события изменилась?»** События неизменяемы, включая
старые версии схем. Читатель обязан понимать все версии: либо через
совместимость реестра схем (лекция 12), либо через **upcasting** —
функцию-переводчик старой версии в новую при чтении. Планировать
эволюцию надо с первого события — поэтому `schema_version` лежит в
конверте с самого начала.

### 6. CQRS: разделение, а не догма о двух базах

> 🖥 **Слайд 11.** CQRS без мифов

**CQRS** (Command Query Responsibility Segregation) — разделение
ответственности: модель для **изменений** (команды, инварианты,
события) и модели для **чтения** (проекции под конкретные экраны) —
разные. Мы уже сделали CQRS в живом сеансе: поток событий — write-модель,
`current_settings` — read-модель.

Два мифа, за которые на собеседованиях снижают оценку:

- **Миф «CQRS = две базы данных».** Разделение — про ответственность
  моделей, не про физику. Проекция может жить в той же PostgreSQL и
  обновляться в той же транзакции, что и запись событий, — синхронная
  проекция, строгая согласованность.
- **Миф «CQRS = обязательно eventual consistency».** Асинхронная
  проекция (через брокер) — частый выбор ради масштабирования чтения,
  но именно выбор с ценой, а не часть определения.

И обратная связь с лекцией 10: помните polyglot-схему, где Cassandra,
Redis и ClickHouse хранили одни и те же показания по-разному? Это и были
read-модели одного потока событий — CQRS в масштабе системы.

### 7. Жизнь с отстающей read-моделью

> 🖥 **Слайд 18.** UX итоговой согласованности

Асинхронная проекция = **итоговая согласованность** между записью и
чтением (лекция 5 — теперь в интерьере). Инженерные приёмы, чтобы жилец
этого не замечал:

- **Подтверждение вместо результата**: «команда принята» — честно и
  мгновенно; результат доедет событием.
- **Optimistic UI**: клиент сам показывает 22°, не дожидаясь проекции, —
  он ведь знает, что отправил.
- **Read-your-writes**: маршрутизировать чтение автора к синхронной
  модели или ждать позиции проекции (лекция 6 упоминала этот трюк для
  реплик — здесь он же).

Главное правило: **не маскировать асинхронность, а проектировать её**.
Интерфейс, который делает вид, что система строго согласована, ломается
самым загадочным для пользователя образом.

### 8. Когда событийные паттерны не нужны

> 🖥 **Слайд 19.** Цена и выбор

Честный чек-лист. Event sourcing стоит дорого: проектирование словаря
событий, версии, снапшоты, обучение команды, непривычные отчёты. Он
окупается, когда:

- история — требование домена (деньги, аудит, комплаенс, телеметрия);
- нужны «вопросы к прошлому» и отладка машиной времени;
- write-нагрузка и read-нагрузка радикально разные (плюс CQRS).

Если у вас справочник комнат в «СмартДоме» — CRUD в PostgreSQL был и
остаётся правильным ответом. Смешивать можно посервисно: биллинг —
event sourcing, справочники — CRUD, интеграция между ними — события
через outbox (лекция 11). Паттерн выбирается на **сервис**, не на
компанию.

## Типичные ошибки (сводка пары)

> 🖥 **Слайд 20.** Типичные ошибки

1. **Командные события** (`SendEmailEvent`) — связность вернулась через
   чёрный ход; тест прошедшего времени провален.
2. **События-изменения полей** вместо доменных фактов — журнал без
   смысла, аудитор плачет.
3. **Правка прошлых событий** — только корректирующие события; плёнку
   не перемонтируют, на неё доснимают.
4. **«CQRS = две БД + eventual consistency»** — разделение
   ответственности путают с физическим разделением.
5. **Маскировка отставания проекции** под строгую согласованность —
   загадочные баги UX вместо честного «принято».
6. **Event sourcing везде** — для CRUD-справочника это дорогой способ
   усложнить себе жизнь.

| Термин | Определение |
| --- | --- |
| Событие | Неизменяемый факт в прошедшем времени; истинен навсегда |
| Команда | Просьба выполнить действие; может быть отклонена |
| Командное событие | Антипаттерн: приказ, замаскированный под событие |
| Конверт события | event_id, schema_version, ts, тип + payload |
| Notification | Тощее событие-уведомление + обратный запрос за деталями |
| Event-carried state transfer | Событие везёт данные; потребители строят копии |
| Event sourcing | События — само хранение состояния; таблица — производная |
| Агрегат | Сущность с собственным упорядоченным потоком событий |
| Свёртка (fold) | Реконструкция состояния применением событий по порядку |
| Проекция (read-модель) | Производное представление под конкретные запросы |
| Снапшот | Кэш свёрнутого состояния; можно стереть и пересчитать |
| Upcasting | Перевод события старой версии схемы в новую при чтении |
| CQRS | Разделение моделей команд и запросов; НЕ обязательно две БД |
| Синхронная/асинхронная проекция | В одной транзакции / через брокер с отставанием |
| Read-your-writes | Автор видит свою запись: маршрутизация или ожидание проекции |
| Сторно | Бухгалтерский предок корректирующего события |

## Ответы

### Ответы: квиз-извлечение (лекция 12)

1. Очередь удаляет потреблённое; журнал хранит записи до retention,
   потребители двигают offset. Реплей — повторное чтение истории с
   нужной позиции.
2. Записи с одним ключом попадают в одну партицию и упорядочены внутри
   неё; между партициями порядка нет.
3. Каждая партиция читается ровно одним участником группы; консюмеры
   сверх числа партиций простаивают.
4. At-least-once доставка + идемпотентный потребитель (дедупликация по
   event_id в одной транзакции с обработкой).

### Ответы: peer instruction

Правильный ответ — **B**: это штатная итоговая согласованность
асинхронной проекции. Мы купили независимое масштабирование чтения и
развязку — заплатили отставанием (PACELC: даже без сбоев платим
задержкой согласованности). UI обязан проектироваться под это:
подтверждение «принято», optimistic-обновление, при необходимости —
read-your-writes для автора.

- A — «баг, такого быть не должно» — отрицание физики: асинхронная
  проекция отстаёт ПО ОПРЕДЕЛЕНИЮ; «чинить» нечего, проектировать — надо.
- C — стрельба из пушки: строгая согласованность всей системы отменяет
  выгоды, ради которых проекцию делали асинхронной; достаточно
  спроектировать UX или дать read-your-writes автору.
- D — чтение свёрткой журнала на каждый запрос панели — это отказ от
  read-модели и её скорости; для «текущих настроек» придётся реплеить
  поток при каждом открытии приложения. Проекция и существует, чтобы
  этого не делать.

### Ответы: квиз-закрепление

1. Тест прошедшего времени: событие — свершившийся факт, истинный
   навсегда (`UserRegistered`); команда — просьба, может быть отклонена.
   Командное событие: `SendWelcomeEmailEvent` — приказ в топике.
2. Уведомление — тощее, но потребитель ходит за деталями синхронно
   (скрытая синхронность); state transfer — данные едут в событии,
   издателя не дёргают, но копии дублируются и стареют.
3. Загрузить события агрегата → свернуть в состояние → проверить
   инварианты → дописать новое событие (с оптимистичной проверкой
   версии потока).
4. Нет. CQRS — разделение ответственности моделей записи и чтения;
   проекция может жить в той же БД и обновляться в той же транзакции
   (синхронная проекция со строгой согласованностью).
