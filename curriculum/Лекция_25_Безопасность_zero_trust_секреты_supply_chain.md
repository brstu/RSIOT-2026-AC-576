## Картина мира: замок пал, да здравствует проверка каждого

> 🖥 **Слайд 5.** Дорожная карта пары

Классическая модель безопасности — **замок и ров** (castle-and-moat):
снаружи враги, внутри свои; строим стену — фаервол, VPN, DMZ — и всё,
что прошло стену, считаем доверенным. Модель умерла не от старости — её
убили три факта современной инфраструктуры. Первый: «внутри» больше не
существует — ваши сервисы живут в облаке, на ноутбуках, в CI-раннерах
GitHub. Второй: атакующий всё равно оказывается внутри — через фишинг,
украденный токен или, как Shai-Hulud, через зависимость, которую вы
сами установили. Третий: внутри стены классическая модель не проверяет
**ничего** — один скомпрометированный под свободно гуляет по всей сети.

Ответ индустрии — **zero trust**: расположение в сети не даёт доверия
вообще. Каждый запрос — от человека или сервиса, снаружи или изнутри —
аутентифицируется, авторизуется и шифруется. Три кита: **проверяй
каждого** (identity вместо location), **минимальные права** (least
privilege: ровно столько, сколько нужно для задачи), **оборона в
глубину** (defense in depth: слои, переживающие пробой соседнего слоя).

Маршрут пары — по слоям обороны: идентичность людей и сервисов →
секреты → шифрование данных → сегментация сети → цепочка поставки кода
→ живой сеанс: моделируем угрозы обновления прошивки «СмартДома».

## Основные понятия

**Определения** (пополним глоссарий в конце):

- **Zero trust** — модель, в которой ни один запрос не получает доверия
  по факту «он из нашей сети»; проверяется идентичность и права каждого.
- **AuthN / AuthZ** — аутентификация («кто ты») / авторизация («что
  тебе можно»); их путают, а это разные вопросы.
- **mTLS** — взаимный TLS: не только клиент проверяет сервер, но и
  сервер клиента, по сертификатам X.509.
- **Секрет** — любые данные, дающие доступ: пароли, токены, ключи API,
  сертификаты, строки подключения.
- **Supply chain (цепочка поставки ПО)** — всё, из чего собирается ваш
  артефакт: зависимости, сборочная инфраструктура, реестры, плагины CI.
- **STRIDE** — чек-лист классов угроз: Spoofing (подмена личности),
  Tampering (подделка данных), Repudiation (отказ от авторства),
  Information disclosure (утечка), Denial of service (отказ),
  Elevation of privilege (повышение прав).

## Ядро пары

### 1. Zero trust: доверие по идентичности, а не по адресу

> 🖥 **Слайд 6.** Периметр умер

Проверьте интуицию на «СмартДоме». Cloud API и Rule engine крутятся в
одном кластере, в приватной сети, наружу торчит только API-шлюз. Нужно
ли шифровать и аутентифицировать трафик **между** Cloud API и Rule
engine?

Периметровое мышление говорит «нет — они же внутри». Посчитаем, кто ещё
«внутри»: каждый под каждого сервиса (включая тот, что собран из
заражённого базового образа), CI-раннер с правом деплоя, ноутбук
администратора с kubeconfig, вчерашний стажёр с доступом «на минутку».
Пробой любого из них в периметровой модели = свободное перемещение по
всей системе (lateral movement). В zero trust пробой одного пода
упирается в следующую проверку через миллиметр.

#### Peer-instruction-вопрос № 1

> 🖥 **Слайды 7–11.** Голосование PI-1 → четыре разбора

Голосуем, обсуждаем с соседом 90 секунд, голосуем снова.

> Cloud API и Rule engine «СмартДома» живут в одном приватном кластере
> за фаерволом; наружу торчит только API-шлюз. Как защищать их

>

### 2. Идентичность: OIDC — людям, mTLS — сервисам

> 🖥 **Слайд 12.** Два мира идентичности

**Люди.** Пользователь «СмартДома» логинится в мобильное приложение не
паролем в ваш API, а через **OIDC** (слой идентификации поверх OAuth2):
приложение отправляет его к провайдеру идентичности (Keycloak, Google),
тот возвращает подписанные токены — `id_token` (кто это) и
`access_token` (что ему можно у API). Для публичных клиентов —
мобильных и SPA — обязателен **PKCE**: одноразовая пара
verifier/challenge, доказывающая, что код обмена перехватил не чужой.
Токены живут коротко, хранятся не в localStorage (XSS утащит), а в
httpOnly-cookie или защищённом хранилище платформы.

**Сервисы.** У Rule engine нет пальца для отпечатка — его идентичность
это **сертификат**. mTLS: при рукопожатии сервер предъявляет сертификат
клиенту, а клиент — серверу; оба проверяют цепочку до доверенного CA.
Выпуск и ротацию сертификатов руками никто не делает — это работа
сервис-меша (лекция 20: sidecar/ambient выдаёт каждому поду сертификат
с его идентичностью и меняет его каждые часы). Поверх аутентификации —
авторизация: политика «Rule engine может звать Alert dispatcher, но не
Billing».

Типичные ошибки: путать аутентификацию с авторизацией («он же
залогинен» — но куда ему можно?); вечные токены и сертификаты; проверка
сертификата отключена «временно, для отладки» (`rejectUnauthorized:
false` — находка № 1 любого аудита).

### 3. Секреты: base64 — это не шифрование

> 🖥 **Слайд 13.** Секреты

Разрушим самый живучий миф курса. Kubernetes Secret выглядит так:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
data:
  password: c3VwZXJzZWNyZXQ=   # выглядит зашифрованным?
```

`c3VwZXJzZWNyZXQ=` — это `supersecret` в **base64**: кодировании для
транспорта, которое обращается одной командой. По умолчанию Kubernetes
хранит секреты в etcd **открытым текстом**; каждый, у кого есть доступ
к etcd или широкий RBAC, читает всё. Минимальная гигиена:

1. **Encryption at rest** для etcd (KMS-провайдер шифрует секреты до
   записи на диск).
2. **RBAC**: право `get secrets` — самое опасное в кластере, раздаётся
   поштучно.
3. **Не коммитить секреты в git** — ни в открытый, ни в приватный:
   Shai-Hulud собирал токены именно из окружений разработчиков и CI.
   Для GitOps-репозиториев (лекция 22: «всё состояние в git!») есть
   решения: **SOPS** и sealed secrets — в git лежит шифротекст,
   расшифровать может только кластер.
4. **Ротация и короткая жизнь**: лучший секрет — который скоро
   протухнет. Менеджеры секретов (Vault и облачные аналоги) выдают
   **динамические** секреты с TTL: утёкший токен умирает сам.

**Проверка.** Найдите секрет в этом предложении: «докер-образ собирается
в CI, куда мы положили переменную `NPM_TOKEN` с правом публикации».
Что случится при заражённой зависимости? (Именно это и случилось
15.09.2025.)

### 4. Данные: envelope encryption за 90 секунд

> 🖥 **Слайд 14.** KMS и конверты · **Слайд 15.** Пауза

Показания «СмартДома» лежат в базе и в бэкапах — их шифруют **at rest**.
Наивная схема «один ключ шифрует всё» ломается о ротацию: сменить ключ =
перешифровать терабайты. Работает **envelope encryption**: данные
шифруются одноразовым **data key**, а data key шифруется мастер-ключом
(**CMK**), который живёт в **KMS** и никогда его не покидает. Рядом с
данными лежит зашифрованный data key (EDK). Ротация CMK = перешифровать
несколько килобайт EDK, данные не трогаются. Приложение не видит
мастер-ключ вообще — только просит KMS «расшифруй мне вот этот EDK», и
каждый такой вызов попадает в аудит.

### 5. Сеть: default-deny, потом разрешения

> 🖥 **Слайд 16.** NetworkPolicy

Zero trust не отменяет сегментацию — она остаётся слоем обороны в
глубину. В Kubernetes это **NetworkPolicy**: сначала запретить всё
(default-deny), потом явно разрешить нужные пары:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-rules
  namespace: smarthome
spec:
  podSelector:
    matchLabels: { app: rule-engine }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: cloud-api }
      ports:
        - protocol: TCP
          port: 8080
```

**Пояснение к примеру.** Читается так: к подам `rule-engine` входящий
трафик разрешён только от подов `cloud-api` и только на 8080. Всё
остальное — при наличии default-deny-политики — отбрасывается.
**Проверка:** `kubectl exec` из пода cloud-api — запрос проходит; из
любого другого пода — таймаут. Типичные ошибки: политики есть, а
default-deny нет (всё, что не описано, разрешено); CNI без поддержки
политик — YAML принят, но ничего не фильтрует (тихий провал — проверять
руками!).

### 6. Supply chain: ваш код — меньшая часть вашего кода

> 🖥 **Слайд 17.** Анатомия атаки · **Слайд 18.** Оборона цепочки

В типичном сервисе «СмартДома» на Node.js ваших строк — сотни,
а строк в `node_modules` — миллионы. Каждая зависимость (и зависимость
зависимости) исполняется **с вашими правами**: в CI — с токенами
деплоя, на проде — с доступом к данным. Цепочка Shai-Hulud теперь
читается как учебник: украденный токен мейнтейнера → заражённая версия
пакета → postinstall у тысяч жертв → кража их токенов → новые заражённые
пакеты. Экспонента.

Оборона выстраивается по цепочке «зависимости → сборка → артефакт»:

- **Зависимости.** Lockfile фиксирует точные версии и хэши
  (`npm ci`, не `npm install` в CI); автоматический аудит уязвимостей;
  задержка обновлений на несколько дней (черви ловятся в первые часы);
  отключение postinstall-скриптов, где возможно.
- **Сборка.** Собирает не ноутбук разработчика, а изолированный
  CI-пайплайн; **SLSA** — шкала зрелости сборки от «кто-то что-то
  собрал» (0) до «изолированная сборка с непереписываемым провенансом»
  (3). **Провенанс** — подписанное свидетельство «этот артефакт собран
  из такого-то коммита таким-то пайплайном».
- **Артефакт.** Образ подписывается (**sigstore/cosign** — подпись,
  прозрачный журнал Rekor), к нему прикладывается **SBOM** — опись
  состава («что внутри»: находить уязвимую библиотеку за минуты, а не
  неделями). Кластер пускает только подписанные образы (admission
  policy).

Заметьте связку: SBOM отвечает «что внутри», SLSA/провенанс — «как и из
чего собрано», подпись — «не подменили ли по дороге». Это разные
вопросы, и нужны все три.

### 7. Живой сеанс: STRIDE для обновления прошивки

> 🖥 **Слайд 19.** Живой сеанс

Строим вместе, на глазах, по шагам (7–10 минут). Сценарий «СмартДома»
из лекции 1: производитель выпускает прошивку → облако раздаёт → Hub
скачивает → Device прошивается. Прогоняем по STRIDE, на каждую букву —
угроза и контроль:

| Буква | Угроза в сценарии | Контроль |
| --- | --- | --- |
| **S**poofing | злоумышленник притворяется сервером обновлений | mTLS/пиннинг сертификата сервера в Hub |
| **T**ampering | прошивку подменили по дороге или в хранилище | подпись прошивки; Device проверяет до установки |
| **R**epudiation | «мы эту версию не выпускали» | подписанный провенанс сборки, журнал выпуска |
| **I**nfo disclosure | из прошивки достали ключи и учётки | не зашивать секреты в образ; ключи — на устройстве |
| **D**oS | сервер обновлений завален, парк без патчей | CDN/edge-раздача (лекция 23), поэтапные волны |
| **E**levation | обновление ставит компонент с лишними правами | least privilege процесса обновления; A/B-разделы и откат |

Ход мысли важнее таблицы: мы **не выдумываем страшилки**, а идём по
чек-листу — поэтому не забываем скучные буквы R и E, которые в реальных
инцидентах стреляют чаще эффектных. Заметьте, как сошлись нити пары:
подпись прошивки — это supply chain (раздел 6), mTLS — идентичность
(раздел 2), «не зашивать секреты» — раздел 3.

**Проверка.** Примените ту же таблицу к сценарию «жилец делится
доступом к дому с гостем»: какие буквы стреляют? (Минимум S — подмена
гостя, E — гость получил права хозяина, R — «я не открывал дверь».)

## Типичные ошибки (запомните до того, как совершите)

> 🖥 **Слайд 20.** Типичные ошибки

1. **«Мы внутри, нам можно без TLS/аутентификации»** — миф периметра;
   lateral movement скажет вам спасибо.
2. **«Секрет в base64 → он зашифрован»** — кодирование ≠ шифрование;
   etcd по умолчанию хранит открытым текстом.
3. **Секреты в git и в переменных CI без нужды** — именно там их
   собирал Shai-Hulud; для GitOps — SOPS/sealed secrets.
4. **`rejectUnauthorized: false` «на время отладки»** — отключённая
   проверка сертификата живёт в проде годами.
5. **NetworkPolicy без default-deny** — всё неописанное разрешено;
   и проверяйте, что CNI вообще исполняет политики.
6. **`npm install` свежайших версий прямо в CI** — lockfile, `npm ci`,
   пауза перед обновлением, отключённые postinstall.
7. **Аудит пишется, но никто не смотрит** — логи безопасности без
   алертов и плейбука реагирования — это архив для постмортема, а не
   защита (свяжите с burn rate из лекции 24: у безопасности тоже есть
   свои SLO).

## Глоссарий

> 🖥 **Слайд 23 (финал).** Вопросы + литература

| Термин | Определение |
| --- | --- |
| Zero trust | Доверие по идентичности и правам, не по расположению в сети |
| Least privilege | Минимальные права, достаточные для задачи |
| Defense in depth | Слои защиты, переживающие пробой соседнего слоя |
| Lateral movement | Перемещение атакующего между системами после первого пробоя |
| OIDC / PKCE | Идентификация поверх OAuth2 / защита обмена кода для публичных клиентов |
| mTLS | Взаимная аутентификация клиента и сервера сертификатами X.509 |
| Encryption at rest | Шифрование данных на диске (etcd, БД, бэкапы) |
| Envelope encryption | Данные шифруются data key, data key — мастер-ключом в KMS |
| KMS / CMK / EDK | Сервис ключей / мастер-ключ / зашифрованный data key |
| SOPS / sealed secrets | Шифротекст секретов в git для GitOps; расшифровка только в кластере |
| NetworkPolicy / default-deny | Правила трафика между подами / «запрещено всё, что не разрешено» |
| Supply chain | Зависимости, сборка, реестры и плагины, из которых рождается артефакт |
| Lockfile | Фиксация точных версий и хэшей зависимостей |
| SBOM | Опись состава артефакта: «что внутри» |
| SLSA / провенанс | Шкала зрелости сборки / подписанное свидетельство «как собрано» |
| sigstore / cosign / Rekor | Экосистема подписи артефактов: подпись / инструмент / журнал прозрачности |
| STRIDE | Чек-лист классов угроз: S, T, R, I, D, E |

## Ответы

### Ответы: квиз-извлечение (лекция 24)

1. Метрики — «что происходит и насколько плохо», трейсы — «где в
   цепочке», логи — «почему именно».
2. Каждая комбинация меток — отдельный временной ряд: миллион device_id
   взорвёт память Prometheus. Уникальные идентификаторы живут в логах и
   трейсах.
3. 1 − SLO = 0,1 % событий или ~43 минуты простоя в месяц — разрешённая
   доля плохого, валюта для рискованных релизов.
4. Burn rate реагирует на скорость сжигания бюджета: настоящий пожар
   будит за минуты, случайный чих не будит вовсе — нет alert fatigue.

### Ответы: peer instruction № 1

Правильный ответ — **B**: внутренний трафик аутентифицируется,
авторизуется и шифруется так же, как внешний, — mTLS плюс политика
«кто кого может звать». NetworkPolicy — полезный дополнительный слой
(оборона в глубину), но не замена идентичности.

- A — миф периметра: «внутри» уже находятся CI-раннеры, ноутбуки,
  чужие базовые образы и заражённые зависимости. Shai-Hulud вошёл
  через `npm install` — фаервол его даже не увидел.
- C — сегментация ограничивает, **кто может дотянуться**, но не
  доказывает, **кто говорит**: скомпрометированный под cloud-api
  проходит любую NetworkPolicy, разрешающую cloud-api. Слой нужный,
  но одинокий.
- D — «не покидает дата-центр» не защищает от того, кто уже внутри
  дата-центра; а трафик между зонами/узлами провайдера — тоже сеть,
  и история знает случаи прослушивания межДЦ-каналов.

### Ответы: квиз-закрепление

1. Проверяй каждого: доверие даёт идентичность, не адрес. Минимальные
   права: ровно столько, сколько нужно задаче. Оборона в глубину:
   каждый слой считает, что соседний уже пробит.
2. OIDC+PKCE — людям (браузеры и мобильные, интерактивный вход через
   провайдера идентичности); mTLS — сервисам (у них нет «логина», их
   идентичность — сертификат). Человеку неудобно жить с сертификатом,
   сервису нечем пройти интерактивный вход.
3. base64 — обратимое кодирование, etcd хранит открытым текстом.
   Слои: encryption at rest (KMS), жёсткий RBAC на `get secrets`,
   внешний менеджер секретов с ротацией/TTL (плюс SOPS/sealed для git).
4. SBOM — «что внутри артефакта»; SLSA-провенанс — «как и из чего он
   собран»; подпись cosign — «его не подменили после сборки». Три
   разных вопроса — нужны все три ответа.
