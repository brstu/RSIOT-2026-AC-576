## Крючок: опечатка, положившая интернет

> 🖥 **Слайд 2.** Крючок: AWS S3, 28.02.2017

28 февраля 2017 года инженер Amazon S3 разбирается с медленным
биллингом. По плейбуку нужно вывести из ротации **несколько** серверов
одной подсистемы. Он вводит штатную команду — с опечаткой в одном
параметре — и выводит из строя **огромный пласт** серверов, включая две
несущие подсистемы хранилища.

S3 в us-east-1 умирает почти на четыре часа. Вместе с ним — GitHub,
Trello, Quora, Medium, вложения Slack: сотни тысяч сайтов держали файлы
в одном регионе одного хранилища (helló, лекция 16). Ущерб индустрии
оценили в ~150 миллионов долларов. Добивающая деталь: подсистемы S3 не
перезапускались **годами**, и их холодный старт занял большую часть тех
четырёх часов.

Ответ Amazon показателен: не «уволить инженера», а **починить
инструмент** — добавить ограничители (guardrails): минимальную скорость
вывода мощностей, проверки безопасности — и проаудировать все похожие
утилиты.

Вопрос залу: опечатка в одной команде — человеческая неизбежность или
проектный дефект? И как строить инфраструктуру, чтобы опечатка
**физически не могла** снести половину интернета?

Сегодняшняя пара — развёрнутый ответ: убрать руки из консоли, описать
инфраструктуру кодом и поставить между человеком и продом ревью и план.

## Картина мира: чертежи вместо устных преданий

> 🖥 **Слайд 5.** Дорожная карта пары

Как сегодня выглядит «инфраструктура руками»: старший инженер помнит,
что прод-кластер создавали два года назад, «там ещё галочку важную
ставили — какую, Витя знал, а он уволился». Второе окружение для
тестов? Неделя кликов и три отличия от прода, о которых узнают в
пятницу вечером. Знакомьтесь: **clickops** — управление инфраструктурой
кликами, устными преданиями и Витиной памятью.

**Инфраструктура как код** меняет носитель истины: не память и не
консоль, а **файлы в git**. Кластер, сети, базы, бакеты — всё описано
текстом, у текста есть история, ревью, откат. Нужно второе окружение —
`apply` тех же файлов с другими переменными. Идея вам уже знакома:
декларативное «желаемое состояние» и машина, приводящая реальность к
нему, — это reconcile из лекции 18, только теперь не для подов, а для
самих кластеров, сетей и облачных аккаунтов.

Аналогия пары — **чертежи здания**. Clickops — стройка «по понятиям»:
что-то возвели, чертежей нет, перестроить страшно. IaC — проектная
документация: хочешь второй такой дом — бери чертежи; хочешь изменить —
правь чертёж, а не стену, и дай архитектору посмотреть (ревью) до
начала работ (plan до apply).

Маршрут пары: зачем IaC → язык HCL и цикл plan/apply → состояние и
дрейф → удалённый state и окружения → модули → ландшафт 2026
(Terraform/OpenTofu) → живой сеанс: кластер «СмартДома» кодом →
секреты и политики. По дороге — два квиза, голосование и пауза.

## Основные понятия

**Определения** (пополним глоссарий в конце):

- **IaC (Infrastructure as Code)** — описание инфраструктуры
  декларативными файлами в системе контроля версий; применение —
  автоматикой, не руками.
- **Clickops** — антипод: управление инфраструктурой кликами в консоли.
- **HCL** — язык конфигурации Terraform/OpenTofu.
- **Провайдер** — плагин к конкретной платформе: aws, kubernetes,
  cloudflare…
- **State (состояние)** — файл-реестр: какие реальные ресурсы
  соответствуют какому коду.
- **Drift (дрейф)** — расхождение реальности с кодом/состоянием
  (обычно — после ручных правок).

## Ядро пары

### 1. Зачем IaC: четыре свойства кода

> 🖥 **Слайд 6.** Зачем IaC

Как только инфраструктура стала текстом, она получает всё, что умеет
текст в git:

1. **История:** кто, когда и зачем менял; `git log` вместо «Витя
   помнил».
2. **Ревью:** изменение прода видно **до** применения — второй глаз
   между опечаткой и катастрофой (вспомните крючок: план изменений
   показал бы «−большой пласт серверов» до нажатия Enter).
3. **Воспроизводимость:** dev/stage/prod из одних файлов — различия
   только в переменных; «у нас на стейдже по-другому» перестаёт быть
   загадкой.
4. **Откат:** плохое изменение — `git revert` и apply, а не
   археология по консоли.

Формула запомнится легко: **clickops — это состояние без истории; IaC —
история, из которой выводится состояние.**

### 2. HCL и цикл plan → apply

> 🖥 **Слайд 7.** Первые ресурсы

Terraform и OpenTofu говорят на одном языке — **HCL**. Опишем кусочек
«СмартДома» (провайдер kubernetes управляет нашим kind-кластером):

```hcl
terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.30"
    }
  }
}

provider "kubernetes" {
  config_path = "~/.kube/config"
}

resource "kubernetes_namespace" "smartdom" {
  metadata {
    name = "smartdom"
  }
}

variable "replicas" {
  type    = number
  default = 2
}
```

**Пояснение к примеру.** `terraform`-блок фиксирует версии (как теги
образов в лабе 5 — никаких «latest»); `provider` — к чему подключаемся;
`resource` — желаемый объект; `variable` — параметры окружений.
Зависимости между ресурсами Terraform строит сам (граф) и создаёт
независимое параллельно.

Рабочий цикл — три команды:

```powershell
terraform init      # скачать провайдеры
terraform plan      # ДИФФ: что изменится, если применить
terraform apply     # применить (спросив подтверждение)
```

**Проверка:** `plan` на неизменном коде показывает `No changes` — это
идемпотентность из лекции 1, у IaC она встроена в цикл.

**Типичные ошибки:** править инфраструктуру и кодом, и руками
(о последствиях — через раздел); не фиксировать версии провайдеров;
запускать apply без чтения plan.

### 3. State: реестр, который нельзя терять

> 🖥 **Слайд 8.** State и дрейф

Откуда Terraform знает, что namespace `smartdom` **уже** создан и его
не надо создавать заново? Из **state** — файла-реестра: «ресурс
`kubernetes_namespace.smartdom` из кода = вот этот реальный namespace».
State — третья вершина треугольника:

- **Код** — как должно быть;
- **Реальность** — как есть;
- **State** — что из реальности принадлежит этому коду.

`plan` сравнивает все три и печатает дифф. Отсюда два следствия:

**Потеря state = амнезия.** Terraform «забывает», чем управлял: ресурсы
живы, но для него их не существует — apply попытается создать
дубликаты. Лечится мучительно (`terraform import` по одному ресурсу).
Поэтому state не удаляют, не правят руками (для хирургии есть
`state mv/rm`) и не хранят на ноутбуке.

**Дрейф.** Коллега «быстро поправил» ресурс в консоли — реальность
разошлась с кодом. `plan` честно покажет расхождение, а `apply` **вернёт
ресурс к описанному в коде состоянию** — ручная правка будет снесена.
Это не баг: источник истины — код (тот же принцип, что «kubectl edit
сотрёт reconcile» из лекции 18). Правило одно: **менять — через код,
всегда.**

### 4. Удалённый state, блокировка, окружения

> 🖥 **Слайд 14 — пауза 60 секунд, затем слайд 15.** Командная работа

**Определения:**

- **Backend** — где живёт state: локальный файл или удалённое
  хранилище (S3-совместимый бакет, Terraform Cloud…).
- **Locking** — блокировка state на время apply: два инженера не
  применят изменения одновременно.

Пока вы один — state лежит рядом с кодом. В команде это заканчивается
быстро: у двоих разные копии state, третий потерял ноутбук. Прод-режим:

- state — в **удалённом backend** (шифрованный бакет), не в git
  (в state попадают чувствительные атрибуты!);
- **блокировка** на время операций — гонки двух apply исключены;
- **окружения разделены**: dev/stage/prod — отдельные каталоги со
  своими state (для простых вариаций есть workspaces, но явные
  каталоги читаются лучше и ломаются реже).

### 5. Модули: функции для инфраструктуры

> 🖥 **Слайд 16.** Модули

Три окружения «СмартДома» = трижды скопированный код? Нет — **модуль**:
каталог ресурсов с интерфейсом из `variables` (вход) и `outputs`
(выход). Один модуль `smartdom-app` — три вызова с разными параметрами:

```hcl
module "telemetry_prod" {
  source   = "./modules/smartdom-app"
  name     = "telemetry"
  image    = "ghcr.io/smartdom/telemetry:1.2.0"
  replicas = 3
}
```

Правила зрелых модулей: версионируйте источники (`?ref=v1.2.3` —
никаких «латестов» и здесь), минимум обязательных переменных, валидация
входов (`validation`-блоки), README с примером. Модуль — это функция:
чистый интерфейс важнее умного нутра.

### 6. Ландшафт 2026: Terraform, OpenTofu и остальные

> 🖥 **Слайд 17.** Ландшафт

История, которую нужно знать инженеру 2026 года: в августе 2023
HashiCorp сменила лицензию Terraform с открытой MPL на ограничительную
BSL — сообщество и вендоры за месяц форкнули последнюю открытую версию,
и родился **OpenTofu** (Linux Foundation, с 2025 — CNCF; в 2025-м саму
HashiCorp купила IBM). Состояние 2026: Terraform — по-прежнему самый
распространённый, OpenTofu — ~12 % практиков и растёт, у него
появились свои плюшки (шифрование state, `for_each` для провайдеров).
Главное для вас: **язык и модель общие** — выучили HCL, plan/apply и
state — умеете оба инструмента. В лабе 7 можно использовать любой.

Соседи по ландшафту — одним взглядом: **Pulumi** — та же модель, но
код на Python/TypeScript вместо HCL; **Ansible** — императивная
настройка того, что внутри машин (пакеты, конфиги) — дополняет, а не
заменяет; **Crossplane** — облачные ресурсы через CRD Kubernetes
(reconcile-подход, доведённый до конца).

### 7. Живой сеанс: «СмартДом» кодом — и лечение дрейфа

> 🖥 **Слайд 18.** Живой сеанс

Строим вместе, на глазах, по шагам (7–10 минут; ход мысли важнее
результата). Задача: **описать кодом namespace и деплой телеметрии — и
увидеть дрейф своими глазами.**

Шаг 1 — пишем `main.tf`: провайдер kubernetes + `kubernetes_namespace`
+ `kubernetes_deployment` телеметрии (образ из лабы 5, реплики из
переменной). Проговариваем: это те же манифесты лабы 5, но теперь с
историей, ревью и переменными.

Шаг 2 — цикл: `init` → `plan` (читаем дифф: «+2 ресурса») → `apply` →
`kubectl -n smartdom get all` — всё на месте. Повторный `plan` —
`No changes`: идемпотентность.

Шаг 3 — устраиваем дрейф: `kubectl -n smartdom scale deploy telemetry
--replicas=5` (руки в консоли!). Снова `plan`:

```text
~ kubernetes_deployment.telemetry
    replicas: 5 -> 2
```

Терраформ **видит** ручную правку и предлагает вернуть код. `apply` —
реплик снова 2. Мораль сеанса в одной строке: реальность подчиняется
коду, а не наоборот — и теперь у вас есть инструмент, где это правило
исполняется автоматически.

### 8. Секреты и политики: два взрослых вопроса

> 🖥 **Слайд 19.** Секреты и policy as code

Коротко о том, что превращает учебный IaC в промышленный:

- **Секреты.** Пароли и токены не живут ни в `.tf`-файлах, ни в git;
  помните: **state тоже содержит секреты** (сгенерированный пароль БД
  окажется в нём открытым текстом) — поэтому backend шифруется, а
  секреты приходят из менеджеров (Vault, SOPS, облачные KMS) — подробно
  в лекции 25.
- **Policy as code.** Раз план — это данные, его можно проверять
  автоматикой до apply: «бакеты не бывают публичными», «prod — только
  из main». Инструменты — OPA/Conftest; это те же guardrails, которые
  Amazon добавил после крючка, только теперь они — часть конвейера.

## Типичные ошибки (запомните до того, как совершите)

> 🖥 **Слайд 20.** Типичные ошибки

1. **Гибрид «код + руки».** Половина инфраструктуры в Terraform,
   половина накликана — plan врёт, apply сносит чужое. Или всё кодом,
   или честно ничего.
2. **State в git / на ноутбуке.** Гонки, потери, секреты в открытом
   виде. Удалённый backend + блокировка + шифрование.
3. **Apply без чтения plan.** План — единственный момент увидеть
   «-destroy 47 resources» до того, как оно случится.
4. **Один state на все окружения.** Опечатка в dev сносит prod.
   Разделяйте каталоги и state.
5. **Секрет в коде «временно».** Git помнит вечно; ротация ключа
   дешевле, чем вычищение истории репозитория.

## Ответы

### Ответы: квиз-извлечение (лекция 20)

1. Apply лишь сохраняет объект; политику исполняет CNI-плагин, и часть
   CNI молча их игнорируют — enforcement проверяется тестом соединения.
2. GatewayClass — реализация (админ платформы); Gateway — слушатель,
   порты/TLS (инфраструктура); HTTPRoute — маршруты и веса (команда
   приложения).
3. mTLS и ротацию сертификатов, ретраи/таймауты, метрики и трейсы,
   маршрутизацию (canary) — из каждого сервиса в общий слой.
4. RollingUpdate меняет поды и не управляет долей трафика; canary
   держит новую версию на малой доле (веса HTTPRoute) под присмотром
   метрик и умеет мгновенно откатиться весом в ноль.

### Ответы: peer instruction № 1

Правильный ответ — **B**: источник истины — код. Plan покажет
`replicas/limit: ночное → из кода`, apply вернёт значение из кода, и
ночная правка исчезнет. Именно поэтому «горячие фиксы руками» обязаны
немедленно попадать в код — иначе их молча снесёт следующий же apply
(возможно, через неделю, когда все забыли о правке).

- A — Terraform сверяет реальность с кодом при каждом plan (refresh) —
  ручное изменение он видит.
- C — Terraform никогда не «подгоняет код под реальность»: направление
  всегда код → реальность (обновится только state-снимок фактических
  значений, но план всё равно вернёт код).
- D — конфликта нет: дрейф — штатная ситуация, plan его показывает,
  apply устраняет.

### Ответы: квиз-закрепление

1. История (git log), ревью до применения, воспроизводимость окружений,
   откат через revert.
2. Реестр соответствия «ресурс в коде ↔ реальный объект». Потеря —
   Terraform «забыл», чем управляет: ресурсы живы, но apply создаст
   дубликаты; восстановление — поштучный import.
3. plan строит дифф (код vs state vs реальность) — читается на ревью;
   apply применяет. Только plan покажет «-destroy» до катастрофы.
4. HashiCorp сменила лицензию Terraform на BSL → сообщество форкнуло
   последнюю открытую версию → OpenTofu (LF/CNCF). Общие — язык HCL,
   модель plan/apply/state; расходятся фичи и управление проектом.
