## Картина мира: ночная смена и конвейер

> 🖥 **Слайд 5.** Дорожная карта пары

На фабрике два режима работы. **Ночная смена** (batch): за день свозят
сырьё, ночью перерабатывают всё разом, утром — готовый продукт. Дёшево,
предсказуемо, результат полный — но вчерашний. **Конвейер** (streaming):
детали обрабатываются по мере поступления, результат — сейчас, но в
каждый момент он «по состоянию на сейчас», а не окончательный.

Данные «СмартДома» живут в обоих режимах: тревога о протечке не может
ждать ночного пересчёта (поток), а месячный отчёт энергопотребления
для биллинга обязан быть точным до копейки и пересчитываемым (пакет).

Главный злодей пары — **время**. Пока данные лежат в таблице, время
простое. Как только данные — это поток событий из ненадёжной сети
(лекция 1 не отпускает), у каждого события становится **два времени**,
и все интересные ошибки растут из их путаницы.

Маршрут: два мира и их цена → batch с безопасным перезапуском →
потоковый процессор → два времени → окна → голосование → watermark и
опоздавшие → живой сеанс со средней температурой → состояние и
exactly-once → Lambda против Kappa. Два квиза, один живой сеанс.

## Основные понятия

**Определения** (пополним глоссарий в конце):

- **Пакетная обработка (batch)** — обработка накопленного, конечного
  объёма данных по расписанию или запуску; результат полный, но отложенный.
- **Потоковая обработка (streaming)** — непрерывная обработка событий
  по мере поступления с малой задержкой.
- **Event time** — когда событие произошло в мире (метка `ts` из
  конверта, лекция 13).
- **Processing time** — когда событие добралось до обработчика.
- **Окно** — конечный интервал, на котором агрегируют бесконечный поток.
- **Watermark** — движущийся порог «события старше T больше не ждём».

## Ядро пары

### 1. Два мира: чем платим за скорость и за полноту

> 🖥 **Слайд 6.** Batch против streaming

| | Batch | Streaming |
| --- | --- | --- |
| Задержка результата | часы/сутки | секунды |
| Полнота | видит весь набор данных | видит «пока пришедшее» |
| Пересчёт при ошибке | перезапустить job | сложнее: состояние, реплей |
| Стоимость и простота | дешевле, проще отлаживать | дороже, тоньше ошибки |

Выбор не «или-или», а «что для какой задачи»: у одной системы обычно
есть и то и другое. Критерий один: **какую задержку терпит потребитель
результата**. Тревога — секунды; счёт за электричество — сутки; отчёт
для налоговой — хоть неделя, лишь бы точно.

### 2. Batch по-взрослому: идемпотентный конвейер

> 🖥 **Слайд 7.** Идемпотентный ETL

Классический конвейер — **ETL**: извлечь (из Cassandra с историей,
лекция 10), преобразовать, загрузить (в ClickHouse). Запускает его
оркестратор — от `cron` до Airflow с DAG'ом зависимостей. Главное
инженерное требование к batch-джобу — **безопасный перезапуск**: джобы
падают, их перезапускают, и повторный запуск не должен удваивать данные.

Рецепт тот же, что всегда (лекции 1, 11 — идемпотентность решает всё):
единица работы — **партиция по дате**, результат — перезаписываемый
атомарно:

```bash
# джоб за конкретный день: перезапуск безопасен —
# выход перезаписывается целиком, ключ идемпотентности = дата
python etl.py --date 2026-08-09 \
  --input cassandra://readings \
  --output clickhouse://daily_agg/2026-08-09
```

**Пояснение к примеру:** день — естественный ключ: упал джоб за 9-е —
перезапустили за 9-е, соседние дни не тронуты. Это же даёт **backfill**:
изменили логику агрегации — прогнали джоб за все дни месяца заново.

**Проверка:** запустите джоб за один день дважды — счётчики строк в
выходной партиции не изменятся после второго запуска.

Типичные ошибки:

1. `INSERT` с дозаписью вместо перезаписи партиции — перезапуск удваивает.
2. Джоб «за всё время» вместо партиций — перезапуск стоит суток.
3. Логика привязана к «сегодня» (`now()`) вместо параметра `--date` —
   backfill невозможен.

### 3. Потоковый процессор: consumer, доросший до вычислений

> 🖥 **Слайд 8.** Стрим-процессор

Ваш консюмер из лабы 4 — уже потоковый процессор: читает журнал,
обрабатывает по событию. Он **stateless**: каждое событие обрабатывается
само по себе (порог тревоги не требует памяти о прошлом).

Интересное начинается со **stateful**-обработки: «средняя температура за
5 минут», «сколько раз дверь открылась за час», «джойн потока показаний
с потоком тарифов». Тут нужны состояние (агрегаты в памяти), окна и
дисциплина времени — и появляются движки:

- **Kafka Streams** — библиотека: обработка живёт прямо в вашем
  Java/Scala-приложении, кластер не нужен;
- **Apache Flink** — отдельный движок, стандарт де-факто для тяжёлых
  stateful-потоков (в марте 2025 вышел Flink 2.0 — первый мажор за
  9 лет); SQL-диалект Flink и крутил глобус Shopify;
- **Spark** — исторически царь batch; его Structured Streaming —
  микробатчи.

Концепции ниже одинаковы во всех движках — учим концепции, не кнопки.

### 4. Два времени: когда случилось и когда доехало

> 🖥 **Слайд 9.** Event time против processing time

У каждого события «СмартДома» два времени:

- **event time** — `ts` из конверта: момент, когда датчик измерил 21,5°;
- **processing time** — момент, когда событие доехало до обработчика.

В идеальном мире они почти совпадают. В реальном — вспомните лекцию 1:
Hub теряет Wi-Fi на 10 минут, буферизует показания и досылает пачкой.
Для всех этих событий processing time — «сейчас», а event time —
«10 минут назад». Считать «среднее за 12:00–12:05» по processing time —
значит записать показания из 12:03 в окно 12:10–12:15: обе пятиминутки
соврут. **Опоздание — не сбой, а штатное свойство распределённой
телеметрии.** Правильные агрегаты считаются по event time — но за это
придётся заплатить (раздел про watermark).

### 5. Окна: как нарезать бесконечное

> 🖥 **Слайд 10.** Три вида окон

Поток бесконечен, а агрегат должен быть конечным — поток нарезают окнами:

- **Tumbling** (кувыркающееся): подряд, без перекрытия — «каждые
  5 минут». Одно событие — ровно одно окно. Для дашбордов и биллинга.
- **Sliding** (скользящее): окно 5 минут, шаг 1 минута — сглаженные
  графики; событие попадает в несколько окон.
- **Session** (сессионное): окно закрывается после паузы неактивности —
  «визит жильца в приложение», «эпизод движения в комнате». Границы
  определяют сами данные.

#### Peer-instruction-вопрос

> 🖥 **Слайды 11–15.** Голосование PI → четыре разбора

Голосуем, обсуждаем с соседом 90 секунд, голосуем снова.

> Дашборд показывает среднее по tumbling-окнам 5 минут (event time).
> Окно 12:00–12:05 закрыто и отображено. Hub восстановил Wi-Fi и дослал
> событие с `ts = 12:03`. Что должна сделать система?

> C. Засчитать в текущее окно 12:15–12:20 — главное, данные не пропали.
> D. Не закрывать окна, пока не отчитаются все датчики, — тогда
> опозданий не будет вовсе.

Разбор — в конце лекции. Подсказка: один вариант молча теряет данные,
один искажает две пятиминутки, один останавливает дашборд навсегда.

### 6. Watermark: договор о том, сколько ждать прошлое

> 🖥 **Слайд 17.** Watermark

Раз события опаздывают, окно по event time не может закрыться «по
будильнику» — вдруг придёт ещё что-то из прошлого? Но и ждать вечно
нельзя (вариант D из голосования). Компромисс — **watermark**:
движущаяся отметка «события старше T мы больше не ждём». Обычно она
вычисляется как «максимальный виденный event time минус допуск»
(например, 30 секунд): watermark прошёл 12:05 + допуск → окно
12:00–12:05 закрывается и публикуется.

Для тех, кто опоздал сильнее допуска, — явная политика из трёх ступеней:

1. **allowed lateness** — короткий период, когда закрытое окно ещё
   можно пересчитать и выпустить поправку;
2. **side output** — совсем поздние события уходят в отдельный поток
   (и ночной batch их учтёт — вот и связка миров из крючка);
3. отбрасывание — только осознанно и с метрикой, сколько отброшено.

Watermark — это ручка компромисса «задержка ↔ полнота»: маленький
допуск — быстрые, но менее полные окна; большой — точнее, но дашборд
отстаёт. Знакомая музыка? Это PACELC (лекция 5) в мире аналитики.

### 7. Живой сеанс: средняя температура, два времени, одна драма

> 🖥 **Слайд 18.** Живой сеанс

Строим вместе (7–10 минут), на доске. Поток датчика s-42, окна
tumbling 5 минут, допуск watermark 1 минута.

**Шаг 1 — события без сюрпризов.** Приходят (event time = processing
time): `12:01 → 20°`, `12:03 → 22°`, `12:06 → 30°`. Спрашиваем зал:
что в окне 12:00–12:05? Среднее (20+22)/2 = **21°**. Событие 12:06 —
уже в следующем окне. Пока просто.

**Шаг 2 — Wi-Fi моргнул.** Событие `ts=12:04 → 40°` (жарко у плиты!)
доехало только в 12:07 (processing time). Считаем двумя способами:

- по **processing time**: 40° падает в окно 12:05–12:10 → окно
  12:00–12:05 показывает 21° (пропустили пик!), окно 12:05–12:10
  завышено чужим значением. Обе цифры врут.
- по **event time**: куда должно попасть 40°? В окно 12:00–12:05.

**Шаг 3 — но окно уже закрыто?** Проверяем watermark: максимальный
виденный event time 12:06, допуск 1 мин → watermark = 12:05. Окно
12:00–12:05 закрылось ровно в момент... разбираем на доске: событие
12:04 пришло при watermark 12:05 — граница! Если допуск 2 минуты —
успевает; если окно уже закрыто — allowed lateness выпускает поправку:
среднее окна 12:00–12:05 обновляется на (20+22+40)/3 = **27,3°**.

**Шаг 4 — вывод на доску.** Правильный ответ зависит не от кода, а от
**политики**: допуск watermark и allowed lateness — это бизнес-решения
(«сколько дашборд может отставать» против «сколько данных можно не
учесть»), и их надо выбирать явно.

**Проверка:** дайте залу событие `ts=11:58 → 25°`, пришедшее в 12:20.
Ответ: сильно позднее — мимо allowed lateness, уходит в side output,
ночной batch внесёт его в дневной отчёт (у batch полнота выше — крючок).

Типичные ошибки:

1. Считать по processing time «потому что проще» — искажение двух окон
   на каждое опоздание.
2. Допуск watermark «с потолка» — измерьте реальное распределение
   опозданий своих Hub'ов (p99 задержки доставки).
3. Отбрасывать поздние события без метрики — молчаливая потеря данных.

### 8. Состояние, чекпоинты и «exactly-once»

> 🖥 **Слайд 19.** Состояние и чекпоинты

Оконные агрегаты — это **состояние** процессора: незакрытые окна живут
в памяти движка. Упал процессор — что с ними? Flink периодически делает
**чекпоинты**: снимки состояния + позиции чтения (offset'ы) в надёжное
хранилище. Рестарт = загрузить чекпоинт + дочитать журнал с
сохранённого offset'а — реплей (лекция 12) снова спасает.

«Exactly-once», которым хвастаются движки, — это чекпоинты плюс
**транзакционные sink'и**: результат окна и позиция чтения фиксируются
атомарно. Знакомая логика? Это outbox/инбокс из лекции 11, встроенный
в движок. И граница та же: exactly-once действует до тех sink'ов,
которые умеют транзакции или идемпотентность; отправка SMS жильцу
из потока — снова ваша идемпотентность, а не магия Flink.

### 9. Lambda против Kappa: сколько раз писать логику

> 🖥 **Слайд 20.** Lambda и Kappa

Как совместить скорость потока и полноту пакета?

- **Lambda-архитектура**: два слоя — speed (поток, быстрые приближённые
  ответы) и batch (ночная «истина», поправляющая поток); витрина
  склеивает. Цена: **одна бизнес-логика написана дважды** и вечно
  расползается.
- **Kappa-архитектура**: только поток; «пересчитать по-новому» = реплей
  журнала с нулевого offset'а новой версией процессора. Возможной её
  делает ровно то, что журнал хранит историю (лекция 12) и события —
  источник правды (лекция 13).

Практика 2026-го — прагматизм: горячий путь потоком, тяжёлые
редкие пересчёты — batch'ем над тем же журналом; но писать одну и ту же
формулу дважды — антипаттерн, за которым следят.

## Типичные ошибки (сводка пары)

> 🖥 **Слайд 21.** Типичные ошибки

1. **Агрегация по processing time.** Каждое опоздание искажает два
   окна; правильные агрегаты — по event time.
2. **Batch-джоб без идемпотентности.** Перезапуск удваивает данные;
   ключ — партиция по дате + атомарная перезапись.
3. **Watermark «на глазок».** Допуск выбирается по измеренному p99
   опоздания, а не по настроению.
4. **Поздние события молча в мусор.** Три ступени: lateness → side
   output → отбрасывание с метрикой.
5. **Вера в сквозной exactly-once.** Он кончается на первом sink без
   транзакций/идемпотентности.
6. **Lambda с расползшейся логикой.** Формула в потоке и формула в
   batch дают разные цифры — и кому верить?

## Глоссарий

> 🖥 **Слайд 24 (финал).** Вопросы + литература

| Термин | Определение |
| --- | --- |
| Batch | Обработка конечного накопленного объёма; полно, но отложенно |
| Streaming | Непрерывная обработка событий с малой задержкой |
| ETL / ELT | Извлечь-преобразовать-загрузить (или загрузить, потом преобразовать) |
| Backfill | Пересчёт исторических партиций после изменения логики |
| Оркестратор | Планировщик конвейеров с зависимостями (Airflow, cron) |
| Stateless / stateful | Обработка без памяти о прошлом / с состоянием (окна, джойны) |
| Kafka Streams / Flink | Библиотека потоковой обработки / отдельный движок (2.0 — 2025) |
| Event time | Когда событие произошло (ts из конверта) |
| Processing time | Когда событие добралось до обработчика |
| Tumbling / sliding / session | Окна: встык / с перекрытием / по паузе активности |
| Watermark | Порог «события старше T не ждём»; max(event time) − допуск |
| Allowed lateness | Период, когда закрытое окно ещё можно поправить |
| Side output | Отдельный поток для сильно опоздавших событий |
| Чекпоинт | Снимок состояния + offset'ов для восстановления |
| Lambda / Kappa | Поток + batch-истина (логика дважды) / только поток + реплей |

## Ответы

### Ответы: квиз-извлечение (лекция 13)

1. Событие — факт в прошедшем времени, истинный навсегда
   (`UserRegistered`); команда — просьба, может быть отклонена.
   Командное событие: `SendWelcomeEmailEvent` — приказ в топике.
2. Загрузить события агрегата → свернуть в состояние → проверить
   инварианты → дописать новое событие (с проверкой версии потока).
3. Нет: CQRS — разделение ответственности моделей; проекция может жить
   в той же БД и той же транзакции (синхронная).
4. Проекция — производная read-модель из событий; после сбоя её
   пересоздают реплеем потока с нужной позиции.

### Ответы: peer instruction

Правильный ответ — **B**: ступенчатая политика. В пределах allowed
lateness окно пересчитывается и выпускается поправка (дашборд честно
обновит цифру); опоздавшие сильнее — в side output, где их подберёт
пакетный досчёт. Данные не теряются и не искажают чужие окна.

- A — молча теряем данные: 40° у плиты не попадёт никуда; для
  телеметрии и тревог это худший исход, тем более без метрики потерь.
- C — та самая ошибка processing time, только вручную: значение из
  12:03 искажает окно 12:15–12:20, а родное окно остаётся неполным.
  Две неверных цифры вместо одной поправки.
- D — окна никогда не закроются: датчик мог утонуть в аквариуме
  (crash-stop, лекция 1) и не отчитается никогда. Именно поэтому
  придуман watermark — договор, сколько ждать прошлое.

### Ответы: квиз-закрепление

1. Event time — когда произошло (ts датчика), processing time — когда
   доехало. Расходятся из-за буферизации Hub при обрывах Wi-Fi, ретраев,
   очередей — опоздание в телеметрии штатно.
2. (а) Окно ещё в allowed lateness → пересчёт и поправка; (б) позднее —
   side output и batch-досчёт; (в) осознанное отбрасывание с метрикой.
3. Единица работы — партиция по дате (ключ идемпотентности) +
   атомарная перезапись выхода партиции; логика от параметра `--date`,
   а не от `now()`.
4. Чекпоинты (состояние + offset'ы атомарно) и транзакционные/
   идемпотентные sink'и. Заканчивается на первом sink, который не умеет
   ни того ни другого (внешние побочные эффекты вроде SMS).
