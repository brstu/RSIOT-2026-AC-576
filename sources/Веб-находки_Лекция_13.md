## 1. Крючок: банковский гроссбух — event sourcing за 500 лет до Kafka

Индустриальный кейс: ни один банк не хранит «только текущий баланс» —
бухгалтерская книга (ledger) есть неизменяемый журнал проводок, а баланс —
производная от журнала. Двойная запись — практика с XV века; регуляторика
и аудит финансовых систем требуют именно историю операций, а не срез.
Современные финтех-архитектуры прямо описывают ledger как event-sourced
запись всех изменений баланса; снапшоты решают проблему счетов с
десятками тысяч событий.

- Banked (финтех): «A bank's ledger is an event sourced record of every
  change made to a balance» —
  <https://medium.com/@banked/event-sourcing-5b7552e1cbe7>
- Production deep dive (снапшоты, реплей на момент времени):
  <https://joudwawad.medium.com/microservices-pattern-event-sourcing-0a18d2e6f7c5>
- Event-sourced architectures for financial systems (аудит, реконструкция
  состояния на любой момент):
  <https://www.researchgate.net/publication/400508233_Event-Sourced_Architectures_for_Financial_Systems>

Второй бытовой пример-кейс: **Git** — commit'ы = события, ветка =
проекция, `git checkout <hash>` = реконструкция состояния на момент
времени. Студенты пользуются event sourcing ежедневно.

## 2. Актуальность практики (2026)

- Специализированные хранилища событий: KurrentDB (бывш. EventStoreDB);
  event sourcing поверх PostgreSQL (Marten) и Kafka (compacted topics
  как state-транспорт). CDC/Debezium — стандарт связки БД → шина
  (уже введён в л. 11).
- Канон различения: CQRS ≠ event sourcing; ES — лишь вариант хранения
  для write-модели. <https://event-driven.io/en/cqrs_facts_and_myths_explained/>

## 3. Типичные заблуждения (→ дистракторы квизов и PI)

- **«CQRS = обязательно две БД и eventual consistency»** — нет: CQRS —
  разделение ответственности команд и запросов; можно в одной БД и даже
  в одной транзакции (синхронная проекция).
  <https://www.kurrent.io/blog/cqrs-dispelling-the-myths/>,
  <https://softwaremill.com/things-i-wish-i-knew-when-i-started-with-event-sourcing-part-2-consistency/>
- **«Event sourcing нужен каждому микросервису»** — нет: цена высока
  (проектирование событий, версии, снапшоты); для CRUD-домена без
  требований аудита — оверкилл.
- **«Событие = команда, только асинхронная»** — нет: событие — свершившийся
  факт в прошедшем времени (OrderCreated), команда — просьба сделать
  (CreateOrder); «командные события» связывают сервисы обратно.
- **«Прочитал сразу после записи — увижу изменение»** — при асинхронной
  проекции read-модель отстаёт; UX обязан честно жить с этим (подтверждение
  «принято», optimistic UI), эмулировать мгновенность — ошибка
  (<https://www.jamesmichaelhickey.com/event-sourcing-eventual-consistency-isnt-necessary/>).
