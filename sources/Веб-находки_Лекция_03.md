## 1. Крючок: сбой Google Cloud 12.06.2025 — null pointer + ретраи без backoff

12.06.2025 в 10:49 PDT Google Cloud лёг глобально примерно на 3 часа:
в систему квот Service Control (проверяет каждый API-вызов) через
автоматическую репликацию попала политика с незаполненными полями.
Спящий код-путь проверки квот (выкачен 29.05.2025 **без feature-флага и
без обработки ошибок**) поймал null pointer — и бинарники Service Control
ушли в crash-loop **во всех регионах сразу**, отдавая 503. Задеты 80+
продуктов Google Cloud и Workspace (Gmail, BigQuery, Cloud Storage,
Vertex AI), а через них — Spotify, Discord, Cloudflare WARP и другие.

Причину нашли за ~10 минут, «красную кнопку» (отключение больного
код-пути) нажали за ~40 минут. Но дальше — вторая волна, наша тема:
задачи Service Control в крупном регионе us-central1 стали перезапускаться
одновременно и хором били в региональную базу Spanner с метаданными
политик. Google в официальном разборе признал: **Service Control не имел
рандомизированного экспоненциального backoff** — инфраструктуру задавил
«эффект стада» (herd effect): против ~40 минут на сам фикс полное
восстановление us-central1 заняло ~2 часа 40 минут от начала сбоя —
перезапуски пришлось троттлить вручную и уводить нагрузку на
мульти-региональные реплики Spanner.

Мораль для лекции: (1) один сетевой компонент на пути каждого вызова —
единая точка отказа; (2) ретраи/перезапуски без экспоненциального backoff
с джиттером превращают восстановление в повторную атаку на самих себя —
даже внутри Google.

## 2. Актуальное состояние gRPC / Protobuf / HTTP (на 09.08.2026)

- gRPC работает поверх **HTTP/2** (мультиплексирование потоков, HPACK);
  поддержка HTTP/3/QUIC — экспериментальная и неравномерная по языкам
  (открытый issue grpc/grpc#19126; обзор kmcd.dev). В лекции: «gRPC = HTTP/2,
  HTTP/3 — пока экспериментально».
- Текущие релизы gRPC — ветка 1.8x (Python 1.82.0, июль 2026); минорные
  номера в лекции не фиксировать — «gRPC 1.x».
- Protobuf: официальная линейка перешла на **Editions** (edition 2023+
  вместо синтаксисов proto2/proto3); политика версий — protobuf.dev.
  Для студентов достаточно proto3-подмножества, editions упомянуть.
- HTTP/3 в вебе растёт: по данным Cloudflare, ~35 % HTTPS-трафика их сети —
  HTTP/3 (Q1 2026, пересказ tech-insider.org — уровень C, в лекцию только
  как «около трети», без точной цифры в тезисах).

## 3. Типичные заблуждения про «надёжный» RPC (→ дистракторы квизов и PI)

1. «Вызов по сети — это как вызов функции, только подлиннее» — классика
   ещё из «A Note on Distributed Computing» (Waldo et al., 1994): сетевой
   вызов имеет частичные отказы и состояние «неизвестно», локальный — нет.
2. «Сеть может доставить сообщение ровно один раз» — exactly-once
   **delivery** в общем случае недостижима; достижима exactly-once
   **processing**: доставка «хотя бы раз» + идемпотентная обработка.
3. «Если сервер вернул ошибку — эффекта точно не было» — неверно: 500
   может прийти и после фиксации записи в БД (упали на отправке ответа).
4. «POST можно повторять — сервер сам поймёт, что это дубль» — без ключа
   идемпотентности сервер не отличит повтор от нового запроса.
5. «Ключ идемпотентности генерирует сервер» — наоборот: ключ генерирует
   **клиент** до первой попытки, иначе при потере ответа клиент слеп.
   Канонический дизайн — Stripe: сервер сохраняет ответ первой попытки
   под ключом (включая ошибки) и на повтор отдаёт сохранённое; ключи
   чистятся после ~24 часов.
6. «gRPC бинарный — значит надёжнее REST» — формат кодирования не меняет
   свойств сети: таймауты, ретраи и идемпотентность нужны одинаково.
