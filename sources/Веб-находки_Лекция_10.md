# Веб-находки для Лекции 10 «Хранилища данных в РС»

Один заход веб-поиска (3 запроса), дата доступа: 09.08.2026.

## 1. Крючок: Discord — триллионы сообщений, Cassandra → ScyllaDB

К началу 2022 у Discord кластер Cassandra на 177 узлов хранил триллионы
сообщений и «горел»: горячие партиции (популярные каналы) создавали
неограниченную конкуренцию запросов и каскадный рост задержек; GC-паузы
JVM давали пилу латентности; дежурные тушили «hot partition» вручную.
Мигрировали на ScyllaDB (тот же протокол, C++ вместо JVM) + написали на
Rust промежуточные data services с request coalescing (сотни одинаковых
чтений схлопываются в один запрос к БД). Итог: 177 узлов → 72, p99 чтения
40–125 мс → 15 мс, p99 записи 5–70 мс → 5 мс.

- Discord engineering: «How Discord Stores Trillions of Messages» —
  <https://discord.com/blog/how-discord-stores-trillions-of-messages>
- The New Stack: разбор миграции —
  <https://thenewstack.io/how-discord-migrated-trillions-of-messages-to-scylladb/>
- InfoQ: <https://www.infoq.com/news/2023/06/discord-cassandra-scylladb/>

Уроки для лекции: (1) выбор хранилища = выбор компромиссов, и на масштабе
компромиссы кусаются; (2) модель данных (партиционирование по каналу)
определяет и скорость, и аварии (hot partition — привет лекции 8);
(3) «протокол тот же, движок другой» — модель данных и API живут дольше
конкретного продукта.

## 2. Актуальность версий (2026)

- Redis: после лицензионной драмы 2024 вернулся к AGPL (май 2025),
  линейка 8.x (vector sets, hash field TTL). Форк **Valkey** (BSD-3,
  Linux Foundation, форк с Redis OSS 7.2.4) — версии 8.1/9.x, в
  бенчмарках ~8 % больше ops/s и −20 % памяти; облака (ElastiCache)
  активно предлагают Valkey. Для курса: «Redis/Valkey» упоминать парой.
  <https://redisson.pro/blog/valkey-vs-redis-comparision.html>,
  <https://sumguy.com/redis-vs-valkey-2026/>
- Cassandra 5.x — актуальная мажорная ветка; ScyllaDB 6.x.
- MongoDB 8.x — актуальная ветка Community.
- ClickHouse — стандарт де-факто колоночной аналитики событий в
  self-hosted мире. Обзор ландшафта:
  <https://www.jusdb.com/blog/open-source-databases-the-complete-guide>

## 3. Типичные заблуждения (→ дистракторы квизов и PI)

- **«NoSQL = schema-less, схемы нет»** — схема не исчезает, а переезжает:
  schema-on-write (БД проверяет при записи) → schema-on-read (схему
  держит код приложения). Неявная схема — тоже схема, но без контроля.
  <https://blog.stackademic.com/nosql-is-not-what-you-think-it-is-95c6fcc2ddb9>,
  <https://enterprisecraftsmanship.com/posts/sql-vs-nosql-you-do-want-to-have-a-relational-storage-by-default/>
- **«LSM всегда быстрее B-дерева»** — LSM выигрывает на записи
  (append-only memtable + compaction в фоне), но чтение может проверять
  несколько уровней (SSTables); B-дерево — чемпион чтения по ключу.
  <https://bytebytego.com/guides/b-tree-vs/>,
  <https://www.usenix.org/publications/loginonline/revisit-b-tree-vs-lsm-tree-upon-arrival-modern-storage-hardware-built>
- **«Redis быстрый — возьмём его для всего»** — in-memory KV не заменяет
  ни аналитику, ни документы, ни durable-хранение истории.
- **Путаница wide-column (Cassandra) и columnar (ClickHouse)** — названия
  похожи, назначение противоположное: первое — OLTP-запись/чтение по
  ключу партиции, второе — OLAP-агрегации по колонкам.
