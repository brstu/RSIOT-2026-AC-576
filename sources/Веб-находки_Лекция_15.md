# Веб-находки для Лекции 15 «Микросервисы и интеграционные паттерны»

Один заход веб-поиска (2 запроса), дата доступа: 10.08.2026.

## 1. Крючок: Prime Video — обратно в монолит и −90 % затрат

Март 2023: команда Video Quality Analysis Amazon Prime Video публикует
разбор о переводе сервиса мониторинга качества аудио/видео **с
микросервисов обратно в «монолит»** (один процесс ECS): оркестрация на
AWS Step Functions упёрлась в лимиты, а видеокадры между шагами
таскались через S3 (дорогие Tier-1 вызовы). Слив всё в один процесс с
передачей данных в памяти, команда сократила инфраструктурные затраты
**на ~90 %** и увеличила масштаб (тысячи потоков; клонирование сервиса
под подмножества детекторов вместо горизонтального масштабирования
каждого шага). Индустрия шумела («Amazon хоронит микросервисы!»), но
суть тоньше: это ОДИН сервис с потоком данных, где границы прошли по
техническим шагам, а не по домену.

- The Stack: «Prime Video service dumps microservices, cuts AWS bill
  90%» —
  <https://www.thestack.technology/amazon-prime-video-microservices-monolith/>
- DevClass: разбор и реакция индустрии —
  <https://devclass.com/2023/05/05/reduce-costs-by-90-by-moving-from-microservices-to-monolith-amazon-internal-case-study-raises-eyebrows/>
- DevOps.com: <https://devops.com/microservices-amazon-monolithic-richixbw/>

Урок для лекции: микросервисы — не цель, а компромисс; границы по
техническим шагам вместо доменных = сетевые вызовы и копирование данных
на ровном месте.

## 2. Актуальность практики (2026)

- Контракты: OpenAPI 3.1 — стандарт описания HTTP API; contract
  testing (Pact) — проверка совместимости потребитель/поставщик.
- «Modular monolith» — легитимная стартовая архитектура в мейнстриме;
  микросервисы — стратегия масштабирования организации, не дефолт.
- Service mesh (Istio/Linkerd, ambient) — в курсе отдельная лекция 20;
  здесь только тизер.

## 3. Типичные заблуждения (→ дистракторы квизов и PI)

- **«Микросервисы = быстрее/масштабируемее по определению»** — сеть
  между модулями добавляет задержку и отказы; выигрыш —
  организационный (независимые команды и деплой), и только при
  правильных границах.
- **«Распределённый монолит»** — сервисы разделены, но связаны:
  синхронные цепочки, релизы только вместе, общие схемы. Микросервисы
  по форме, монолит по сути.
  <https://vfunction.com/blog/distributed-monolith-architecture/>
- **«Общая БД на несколько сервисов — это удобно»** — скрытая
  связность: сервисы общаются через таблицы в обход API; database-per-
  service — ядро автономии.
  <https://medium.com/@subham11/the-shared-database-anti-pattern-c87013d2dcb2>
- **«Дробить как можно мельче»** — nanoservices: каждый вызов функции
  становится сетевым; границы — по bounded context, а не по функциям.
  <https://www.designgurus.io/blog/10-common-microservices-anti-patterns>
