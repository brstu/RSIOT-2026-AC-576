# Веб-находки для Лекции 09 «Отказоустойчивость и chaos engineering»

Один заход веб-поиска (3 запроса), дата доступа: 09.08.2026.

## 1. Крючок: глобальный сбой Google Cloud 12.06.2025

Суть: изменение кода в Service Control (компонент проверки квот/политик на
пути КАЖДОГО API-запроса) вышло без обработки ошибок и без feature-флага.
12 июня в систему попала политика с пустыми полями → null pointer → бинарь
Service Control ушёл в crash loop **во всех регионах одновременно**.
Сотни сервисов Google Cloud и Workspace (Compute Engine, Cloud Storage,
BigQuery, Gmail, а также Cloudflare WARP, Spotify, Discord) отдавали 503
около 3 часов. Регион us-central1 восстанавливался дольше всех: логика
повторов не имела рандомизированного backoff — восстановление добил
«шторм» ретраев (herd effect), инженеры вручную дросселировали трафик.

- ThousandEyes: анализ сбоя —
  <https://www.thousandeyes.com/blog/google-cloud-outage-analysis-june-12-2025>
- The Register: «Google Cloud caused outage by ignoring its usual code
  quality protections» —
  <https://www.theregister.com/2025/06/16/google_cloud_outage_incident_report/>
- ilert: конспект постмортема —
  <https://www.ilert.com/postmortems/google-cloud-outage-june-2025>

Ключевые уроки для лекции: (1) один компонент на пути каждого запроса =
максимальный blast radius; (2) ретраи без джиттера превращают восстановление
во вторую волну; (3) деплой без канарейки/флага — отказоустойчивость
начинается до инцидента.

## 2. Актуальность инструментов chaos engineering (2026)

- Chaos Mesh (CNCF, изначально PingCAP) — самый широкий набор точечных
  отказов: pod/network/IO/stress/time/kernel/DNS/HTTP, свой дашборд;
  единственный с TimeChaos (сдвиг часов) и JVMChaos.
- LitmusChaos (CNCF) — ChaosHub (50+ готовых экспериментов, включая
  AWS/GCP/Azure), ChaosCenter UI, GitOps-подход к хаосу.
- Сравнения 2026: <https://reintech.io/blog/litmuschaos-vs-chaos-mesh-kubernetes-chaos-tool-comparison-2026>,
  <https://kubernetes.qa/blog/chaos-mesh-vs-litmus/>
- Классика: Chaos Monkey (Netflix), Gremlin (SaaS), Pumba (Docker).
- В лекции инструменты даём обзорно (K8s у студентов только с лекции 18);
  практический акцент — принципы эксперимента и tc netem/kill pod.

## 3. Типичные заблуждения (→ дистракторы квизов и PI)

- «Буфер побольше решит перегрузку» — нет: если потребитель стабильно
  медленнее производителя, любой буфер заполнится; неограниченные очереди —
  самая частая ошибка backpressure
  (<https://sreschool.com/blog/backpressure/>,
  <https://www.tedinski.com/2019/03/05/backpressure.html>).
- «Ретраить надо всё» — нет: ретраи уместны для transient-ошибок; повтор
  429/503 (сервис сбрасывает нагрузку) усиливает перегрузку
  (<https://dzone.com/articles/overcoming-the-retry-dilemma-in-distributed-systems>).
- «Ретраи на каждом уровне цепочки» — умножение повторов (3×3×3);
  ретраить у краёв системы, не в середине
  (<https://www.tedinski.com/2019/03/05/backpressure.html>).
- «Circuit breaker — это просто ретрай наоборот» — нет: breaker отказывает
  быстро (fail fast) и даёт зависимости отдышаться; без него backpressure
  сам по себе копит заблокированные потоки вверх по цепочке
  (<https://codelit.io/blog/backpressure-flow-control>).
