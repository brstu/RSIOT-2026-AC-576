## 1. Крючок: Roblox 28–31.10.2021 — 73 часа без игры из-за одного непартиционированного кластера

Официальный постмортем Roblox «Return to Service». 28 октября 2021 года
платформа (тогда ~50 млн игроков в день) легла целиком на **73 часа**.
Виновник — **один центральный кластер Consul**, через который ходили
service discovery и координация ВСЕХ рабочих нагрузок компании.

Технические детали (проверено по постмортему и разборам):

- За день до сбоя включили новую функцию **streaming** в Consul. Под
  необычно высокой нагрузкой чтений/записей дизайн streaming создал
  **contention на одном Go-канале**: записи блокировались, эффективность
  падала — классическая «горячая точка», только не на диске, а в
  конкурентности.
- Второй, независимый фактор: патологическая деградация **BoltDB**
  (хранилище Raft-лога Consul) — freelist рос и не освобождался,
  каждая запись дорожала.
- Диагноз затянулся на дни, потому что **мониторинг сам зависел от
  Consul** — циклическая зависимость наблюдаемости.
- Замена серверов 64 → 128 ядер не помогла (проблема была в contention,
  а не в мощности) — вертикальное масштабирование против горячей точки
  бессильно.
- Ключевой вывод постмортема для нашей темы: один кластер Consul на всё
  — единая точка отказа и «горячий» компонент; план исправления —
  **партиционировать Consul на несколько кластеров** по нагрузкам и
  добавить географически отдельный ЦОД.

Источники:

- [Roblox — Return to Service 10/28–10/31 2021 (официальный постмортем)](https://about.roblox.com/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021)
- [InfoWorld — Roblox's cloud-native catastrophe: a post mortem](https://www.infoworld.com/article/2334415/robloxs-cloud-native-catastrophe-a-post-mortem.html)
- [Data Center Dynamics — Roblox adds data center after 73-hour outage](https://www.datacenterdynamics.com/en/news/roblox-adds-data-center-after-73-hour-outage/)

Уровень доверия: A (официальный постмортем; детали streaming/BoltDB
сверены с ним).

Примечание для честности подачи: это инцидент «горячего центрального
компонента и отсутствия партиционирования», а не «горячего шарда
партиционированной БД» — в лекции подаётся именно так.

## 2. Горячие партиции в DynamoDB — задокументированный режим отказа (на 10.08.2026)

- AWS-документация прямо описывает троттлинг из-за горячего ключа:
  лимиты **на партицию** — 3000 RCU и 1000 WCU в секунду; один
  «знаменитый» ключ упирается в них, даже если суммарная ёмкость
  таблицы в разы больше.
- Официальные рекомендации AWS: **write sharding / соль в ключе**
  (случайный или вычисляемый суффикс), равномерный дизайн ключа,
  кэширование горячих чтений (DAX).
- **Adaptive capacity** изолирует горячий ключ и автоматически
  **сплитит партицию** по нагрузке (split for heat), но не спасает,
  когда весь трафик бьёт в ОДИН ключ — предел одного ключа остаётся.

Источники:

- [AWS Docs — Key range throughput exceeded (hot partitions): mitigation](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/throttling-key-range-limit-exceeded-mitigation.html)
- [AWS Docs — Troubleshooting throttling in Amazon DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TroubleshootingThrottling.html)

Уровень доверия: A (официальная документация AWS).

## 3. Consistent hashing и партиционирование в проде (проверка актуальности, 10.08.2026)

- **Cassandra**: Murmur3Partitioner (64-битный хэш) — дефолт с 1.2;
  виртуальные узлы (vnodes). Важно: дефолт `num_tokens` **снижен с 256
  до 16** начиная с Cassandra 4.0 — избыток vnodes замедлял repair и
  стриминг данных; «чем больше, тем лучше» не подтвердилось практикой.
- **Redis Cluster**: не кольцо, а **16384 фиксированных хэш-слотов**
  (`CRC16(key) mod 16384`), слоты перекладываются между узлами целиком —
  учебниковая реализация стратегии «фиксированное число партиций».
- **Kafka**: дефолтный партиционер — `murmur2(key) mod numPartitions`;
  это честный `hash mod N`, который работает только потому, что число
  партиций топика **менять нельзя без потери привязки ключей** —
  партиции задаются с запасом при создании топика.
- **DynamoDB**: статья Dynamo (2007) — родоначальник consistent hashing
  с виртуальными узлами в промышленных KV-хранилищах.

Источники:

- [DataStax Docs — Murmur3Partitioner (Cassandra)](https://docs.datastax.com/en/cassandra-oss/3.x/cassandra/architecture/archPartitionerM3P.html)
- [The Last Pickle — Impacts of changing the number of vnodes in Apache Cassandra](https://thelastpickle.com/blog/2021/01/29/impacts-of-changing-the-number-of-vnodes.html)
- [Cassandra Docs — cassandra.yaml (num_tokens: 16)](https://cassandra.apache.org/doc/4.1/cassandra/configuration/cass_yaml_file.html)
- [OneUptime — How Redis Cluster hash slots work (16384 slots)](https://oneuptime.com/blog/post/2026-03-31-redis-cluster-hash-slots-16384/view)
- [Rasztabiga — Consistent hashing: the pattern that saves you when nodes die](https://rasztabiga.me/blog/consistent-hashing)

Уровень доверия: A для документации Cassandra/DataStax/AWS; B для
блог-разборов (сверены между собой).

## 4. Типичные заблуждения студентов по теме (→ дистракторы квизов и PI)

1. **«hash(key) % N — нормальный способ шардировать»** — при изменении N
   переезжают почти все ключи (решардинг-катастрофа); работает только
   при жёстко фиксированном N (Kafka) или поверх фиксированных слотов
   (Redis Cluster).
2. **«Ключ по времени удобен для телеметрии»** — монотонный ключ
   (timestamp, auto-increment) собирает все свежие записи в одной
   партиции: горячий хвост при холодных остальных узлах.
3. **«Нарежем шардов побольше про запас — это бесплатно»** — опровергнуто
   практикой: Cassandra снизила дефолт vnodes 256 → 16 (repair и
   streaming деградировали); у Kafka каждая партиция стоит файлов,
   памяти и времени фейловера.
4. **«Партиционирование = репликация»** — путают распил данных на части
   с копированием данных; в реальных системах они комбинируются
   (каждый шард реплицирован).
5. **«Добавим узлов — горячий ключ рассосётся»** — все запросы к одному
   ключу всё равно приходят на одну партицию (случай Roblox: 128 ядер
   вместо 64 не помогли).

Источники: те же, что в №№ 1–3 (постмортем Roblox, AWS Docs, The Last
Pickle).
