## 1. Крючок: GitHub 21.10.2018 — 43 секунды разрыва, сутки последствий

Классический постмортем про фейловер и split brain. 21 октября 2018,
22:52 UTC: плановая замена сбоящего оптического оборудования 100G
обрывает связь между сетевым хабом восточного побережья США и основным
восточным дата-центром GitHub. Связь восстановлена через **43 секунды**,
но за это время оркестратор фейловера (Orchestrator) счёл восточный ДЦ
недоступным и промоутил реплики MySQL на западном побережье в новые
primary. Итог: на восточном primary остался хвост записей, не доехавший
на запад; западные primary тем временем приняли собственные записи —
две расходящиеся истории данных (split brain по данным). Возврат назад
означал бы потерю подтверждённых записей, поэтому GitHub выбрал
fail-forward: западный ДЦ остался primary (кросс-континентальная
задержка ~60 мс на каждую запись), восточные кластеры восстанавливали
из бэкапов и досинхронизировали. Деградация сервиса — **24 часа
11 минут**: webhooks и Pages задерживались, часть данных временно
показывалась устаревшей.

Мораль для лекции: (1) фейловер — не кнопка, а самая опасная операция
лидерной репликации; (2) асинхронная репликация + автопромоушен =
готовый рецепт расходящихся историй; (3) «вернуть старого лидера» после
расхождения нельзя без сверки/отката — отсюда фенсинг и консенсус
(трейлер лекции 07).

## 2. Актуальные механизмы репликации PostgreSQL 17/18 (на 10.08.2026)

- Текущая мажорная версия — **PostgreSQL 18** (вышла 25.09.2025);
  17.x — предыдущая поддерживаемая ветка.
- Физическая (streaming) репликация гоняет **WAL**; `synchronous_commit`
  — лестница долговечности на каждую транзакцию: `off` → `local` →
  `remote_write` → `on` (= remote_flush) → `remote_apply`.
- `synchronous_standby_names` поддерживает **кворумную синхронную
  репликацию**: `FIRST N (...)` / `ANY N (...)` — «дождись любых двух
  из трёх» прямо в конфиге.
- **Слоты репликации** удерживают WAL для отставшей/логической реплики;
  обратная сторона — забытый слот раздувает диск primary. В PG 18
  появился `idle_replication_slot_timeout` — автоматическое
  инвалидирование простаивающих слотов.
- PG 18: синхронизация **логических failover-слотов** на физический
  standby (подписчики логической репликации переживают фейловер
  primary), конфликт-репорты логической репликации в
  `pg_stat_subscription_stats`, `pg_createsubscriber --all`.

## 3. Redis: асинхронная репликация и честные ограничения WAIT

- Репликация Redis **асинхронна по умолчанию**: клиент получает OK до
  того, как запись доехала до реплик; при фейловере подтверждённые
  записи могут быть потеряны.
- Команда `WAIT numreplicas timeout` блокирует клиента, пока запись не
  подтвердят N реплик, — сужает окно потери, **но не превращает Redis в
  строго консистентную (CP) систему**: документация говорит это прямым
  текстом; при фейловере подтверждённые записи всё равно могут пропасть
  в зависимости от конфигурации персистентности.
- Отличная иллюстрация тезиса лекции «подтверждение ≠ долговечность» и
  «синхронность — спектр, а не переключатель».

Источники:

## 4. Заблуждения про «синхронная репликация = без потерь и бесплатно» (→ дистракторы)

1. «Включил синхронную репликацию — потерь нет и ничего не стоит» —
   стоит: каждая запись ждёт RTT до реплики (и самую медленную из
   обязательных); при падении единственного sync-standby записи
   **блокируются** — платим доступностью записи.
2. «Semi-sync повышает доступность» — наоборот, понижает: добавляется
   ещё один способ не закоммитить запись (нет живого подтверждающего
   фолловера). Semi-sync покупает долговечность, а не доступность
   (разбор Percona).
3. «Semi-sync-реплика — всегда самая свежая» — не обязательно: подтверждает
   получение (receive/relay log), а не применение; MySQL AFTER_SYNC
   закрывает потерю на фейловере, но лаг применения остаётся.
4. «Кворум W+R>N даёт линеаризуемость» — нет: даёт пересечение множеств
   при чтении, но гонки записи/чтения, sloppy quorum и частичные записи
   ломают строгий порядок (Kleppmann, гл. 5; связка с лекцией 05).
5. Цена вопроса в цифрах: у MySQL semi-sync типичная просадка
   производительности ~5–15 %, подтверждение ~1–5 мс в быстрой локальной
   сети и резко хуже с расстоянием (агрегаторы метрик репликации).
